01P0~P3 能不能改？逐条落地手册

先回答你的问题：都能改，而且大部分不难。真正卡你的不是技术，是「值不值得在发布前花时间」。下面每条我给你三样东西——人话解释、具体怎么改、我的建议（做/缓/不做）。

先看总原则：发布前只有 P0 必须动（因为会直接砸口碑）。P1 挑「性价比最高的 1~2 个」做。P2/P3 一律推迟到发布后——现在做它们等于「发布会前夜还在装修仓库」，投入产出比极低。

P0① 测试套件 flaky（间歇性失败）

人话解释你的测试在「快机器 + 没别的事」时全绿，但慢机器或同时在跑别的东西时，个别用例会莫名其妙失败。这就像体检报告偶尔出个假阳性——不影响代码本身，但会毁掉别人对你的信任。

为什么是 P0发布后，贡献者 clone 下来第一件事就是 npm test。如果红了，他第一反应是「这项目连测试都跑不过」，直接关掉页面。你的整个信任锚就是「质量闸门」，flaky 等于自己砸锚。

我查到的实锤vitest.config.ts:21 设了 testTimeout: 30000（30 秒）；有 12 个测试文件用了 setTimeout / 长超时，它们是首要嫌疑：chatQualityFixes / decisionService / fullDuplexController / llmProvider / longConversation / loopEngine / reproduceDegen / stabilityFixes / trayMenu / v330Team / voiceLoop / workspaceProgress。

怎么改三步，从易到难：
1. 先定位：写个循环脚本跑 npx vitest run 20 次，记录哪几个文件失败 → 大概率就是那 12 个里的。
2. 对症下药：时序类（等真实计时器）改用 vi.useFakeTimers() + vi.advanceTimersByTime()，别等真时间；mock 清理类检查 afterEach 是否漏了 vi.restoreAllMocks()。
3. 兜底：确实无法确定化的，给那个用例单独调高 testTimeout 或标 .retry(2)（vitest 支持），并加注释说明原因。

工作量半天到一天（定位占一半）。

风险低。改的是测试不是产品代码。

✅ 发布前必做
P0② README 数字与代码对齐

人话解释你 README 里写的数字已经过时了——这不是撒谎，是「没来得及更新」。但读者不知道，他会以为你在虚报。

我实测的差距测试文件：README 写 242，实际 266（涨了）；agentRunner.ts：README 自曝 4117 行，实际 4285 行。方向都是「实际更好/更大」，但数字对不上就是硬伤。

怎么改发布前跑一遍采集脚本，把 README、BENCHMARKS.md 里所有数字刷新：find tests -name "*.test.ts" | wc -l、wc -l electron/agentRunner.ts、npx vitest run 的结果、npx tsc --noEmit --strict 的结果。顺便在 README 顶部加一句「数据采样：2026-XX-XX」——你已经这么做了，继续保持。

工作量1 小时。

风险零。

✅ 发布前必做（性价比最高）
P1③ 拆 agentRunner.ts（4285 行单体）

人话解释一个文件 4285 行，相当于一本中篇小说的长度塞在一章里。你自己写的时候有上下文所以不觉得，但外部贡献者打开会直接懵——「LLM 调用、ReAct 循环、工具执行」全糊在一起。

怎么改按职责切 3~4 个文件，纯搬运不改逻辑（这样最安全）：
· agentRunner.llm.ts — LLM 调用与重试
· agentRunner.loop.ts — ReAct 主循环与轮次保护
· agentRunner.tools.ts — 工具执行与结果解析
你已经有两个「拆出来的先例」：agentRunner.constants.ts / agentRunner.preprocess.ts——顺着这个路子继续拆就行。

工作量1~2 天（搬运本身快，但你要确保 266 个测试文件全绿——这是保护网）。

风险中。纯重构也可能碰坏隐式依赖，所以必须「拆一次跑一次测试」。

我的建议：发布前别拆。理由——它不影响用户使用，只影响「别人读你的代码」。而发布第一周，没人会去读源码，大家都在看 README 和演示视频。等有了第一个外部 PR 再拆，那时候你还有动力。现在拆是「优化了没人看的东西」。

⚠️ 发布后做（不急）
P1④ 给路由加「确定性逃生舱」（/yak · /recha）

人话解释你现在最大的槽点是「同一句话问两次，可能一次派给 Yak、一次 Lumina 自己答」——因为派活是「模型自己判断」，不是写死的规则。专业用户最恨这个。

好消息你已经有现成的命令系统了！electron/chatCommands.ts 里已经支持 /switch、/compact、/plan 等命令，在聊天框内前置拦截、不发给 LLM。加 /yak /recha /ask-lumina 三个命令只是「往注册表里加条目」的事——让用户能手动静派。

怎么改在 COMMANDS 数组里加 3 条定义，handler 里直接调 delegationManager.delegate() 指定目标（跳过 routingDecider）。给专业用户一个「我就是要 Yak 干」的确定性入口。

顺手修一个 bug：我读 chatCommands.ts 时发现 /switch 的提示文案还写着旧角色名——usage: '/switch <luna|ray|sora|assistant>'（第 108 行），但你现在的角色早就改名成 lumina / yak / recha 了。用户照这个提示输入会失败。这是 1 分钟的修复，但属于「用户一眼可见的错」，建议顺手改掉。

工作量加命令 2~3 小时；顺带修文案 1 分钟。

风险低。命令是旁路，不影响主链路。

✅ 建议做（性价比高，直接解决最大槽点）
P1⑤ IM 渠道端到端真机验证

人话解释你写了 7 个 IM 适配器（telegram / discord / slack / qq / dingtalk / wechat / openclaw），但只把 Telegram 默认开着，其余要用户自己配凭据，而且你自己都没真机跑通过。这就像「菜谱写好了，但没下过锅」。

怎么改只做一件事：把 Telegram 端到端真机跑通（配好 bot token → 手机发消息 → 收到 Lumina 回复 → 录个屏）。其余 6 个在 README 里如实标注「已接线，未端到端验证」。

工作量半天（Telegram 最好配）。

风险低，但需要你有个真 Telegram 账号 + bot。

✅ 建议做（哪怕只跑通 1 个）
P2⑥ no-explicit-any 棘轮 & ⑦ 技能生态占位

any 警告README 说约 5100 条。我粗查 src+electron 里的 : any 写法约 1694 处（口径不同，但量级确实大）。你已经用「棘轮」管住了（只减不增）——这就够了，发布前别碰。一次性清 any 极易引入类型 bug，得不偿失。

技能生态我之前说「生态是空的」需要修正：skills/ 目录里其实有 8 个内置示例技能（browser_click_smart / code_review_smart / file_search_smart / web_search_multi 等）。所以准确说法是——「有内置示例，但无第三方生态」。这个建议在 README 里说清楚，比「生态是空的」更准确，也更容易被接受。

⏸ 发布后做（现在别碰）
P3⑧ 记忆 CJK 中文分词

人话解释你的记忆召回对中文用的是「字符级 unigram + bigram」（没词典，纯按字切）。比如「苹果手机」会切成「苹/果/手/机/苹果/果手/手机」——能召回，但不如真正的分词准。

怎么改评估接一个轻量中文分词（如 nodejieba），或干脆接一个本地 embedding 服务（你已经有 dense 语义向量 开关，默认关）。

工作量1~2 天 + 引入新依赖。

风险中。新依赖 = 新打包问题（你是 Electron，原生模块要 rebuild）。

⏸ 远期内做（现在完全不用管）

02「该抄清单」人话解读

这份清单来自我对 4 个竞品的拆解。先说清楚：不是每个都值得抄。我按「抄了能立刻提升你项目多少」给你排了序，并说清「为什么它好、在你项目里怎么落地」。

最值得抄① H5 手机远程访问（来自 cc-haha）

它是什么用手机浏览器扫码，就能接入电脑上的会话——看进度、补指令、审批权限。锁屏切后台都不打断正在跑的任务。

为什么好你已经有一个本地 REST API（localhost:3456，10+ 端点）。把它暴露成一个手机能访问的简单页面，就等于给你加了一个「远程遥控器」——不用做原生 App、不用上架应用商店。

怎么落地你已有 electron/api/ 模块。加一个极简 H5 页（一个输入框 + 一个消息流 + 审批按钮），用局域网 IP 访问即可。第一版甚至不用鉴权（局域网内），后续加个 token。

为什么对你特别重要你的核心卖点是「桌宠必须常驻」——那「人不在电脑前也能管它」就是刚需。cc-haha 和 openclaw 都证明了这条路。这是你「常驻架构」优势的自然延伸。

✅ 最该抄的一个（放大你的常驻优势）
值得抄② 记忆的「会话级双开关」+「不记什么」清单（来自 MiniMax Code）

它是什么对话开始前能设定「这次用不用记忆」、开始后不能改；对话中能随时调「要不要生成记忆」。再给用户一份明确的「我绝不记什么」清单（一次性状态、临时日志、敏感密钥、过期细节）。

为什么好你有很强的记忆系统，但用户对「AI 记住了我什么」是有恐惧的。双开关 + 明确清单 = 把控制权交还给用户，同时显得你对隐私有边界感。这是「信任设计」，成本极低、收益极高。

怎么落地你已有记忆设置页。加两个开关 + 一段说明文字就行，不用改记忆引擎本身。

✅ 值得抄（1 天，纯 UI + 文档）
按需抄③ 记忆校对 UI（来自 N.E.K.O 的 /memory_browser）

它是什么一个可视化界面，让用户浏览、修正、删除 AI 长期记住的内容。

为什么好你的 README 写了「记忆剧场」——如果它已经能可视化浏览，那你其实已经有了雏形，缺的是「能编辑/删除」。补上编辑能力，就追平了 N.E.K.O 的这一块。

怎么落地在现有记忆剧场面板上加「编辑 / 删除 / 标记错误」按钮，接到已有的 memoryStore 写接口。

⚠️ 如果记忆剧场已存在，这是小改；否则缓做
按需抄④ Agent Teams 依赖泳道画布（来自 cc-haha）

它是什么一个可视化画布，把多个 Agent 的依赖关系、任务流、通信画成泳道图。

关键发现我看了你的 src/panels/ 目录——你已经有 SwimlaneCanvas.tsx、TeamTopologyView.tsx、TeamPanel.tsx 了！也就是说这块你已经做了，只是可能没在 README 里突出。

我的建议不是「抄」，而是「把你已经有的东西讲出来」。去 README 的截图区加一张泳道图，这比新做一个功能划算得多。

⚠️ 你可能已经有了——先盘点，别重复造
按需抄⑤ 模型 trace 面板（来自 cc-haha）

它是什么本地记录每一轮模型请求的状态和耗时，可搜索筛选，快速定位「哪次调用卡死了 / 失败了」。

为什么好你有一个 team/llmTrace.ts——看起来已经有底层能力了，缺的是「把它做成一个可搜索的面板」。

怎么落地如果有数据源，加一个面板展示即可；如果只是内部日志，做成可导出的日志查看器。

⚠️ 先确认 llmTrace 是否已有数据源
锦上添花⑥ Goal 机制（来自 MiniMax Code）

它是什么用户设定一个「可验证的最终目标」，Agent 持续推进直到达标或阻塞，而不是一问一答。

为什么好这是「从助手到代理」的关键一跃。但它需要很强的任务持久化 + 状态恢复能力——你有 asyncTaskManager / teamCheckpoint，底子够，但工程量不小。

我的建议概念上很吸引人，但属于「v1.0 之后」的事。发布阶段别碰。

⏸ 远期（很酷但工程量大）
锦上添花⑦ ACP 协议 / openclaw A2A adapter（来自 MiniMax / openclaw）

它是什么让别人能把你接进第三方编辑器/宿主（ACP），或者让你借用 openclaw 的 30+ 渠道（A2A adapter）。

关键发现你已经有 electron/channels/openclaw/openclawClient.ts！也就是说你已经在做这件事了。N.E.K.O 也做了 brain/openclaw_adapter.py——这是行业共识方向。

我的建议方向对，但发布时只需要在 README 里说「已支持 openclaw 适配器」，不用深入做 ACP（那是给企业集成用的，你的用户还不需要）。

⚠️ 已在做——README 里讲清楚即可

2.1 「该抄清单」一句话总结

盘点之后我发现一个好消息和一个提醒：

✅ 好消息：你以为要「抄」的东西，你其实已经做了一半——泳道画布、拓扑图、llmTrace、openclaw 适配器，代码里都有。你缺的不是功能，是把已有的东西讲出来。

03测评报告怎么读 + 决策指南

那份报告信息量很大，怕你看晕。这一节教你怎么「抓重点」——哪些数字该信、哪些该存疑、以及你到底该做什么决定。

3.1 报告里三类信息，可信度不同

类别可信度怎么用
我实机跑出来的（tsc 0 错误、266 测试文件、218 commits、4285 行）高可直接引用，甚至可写进 README
我逐行读代码确认的（权限闸门、路由降级、对抗评审、情绪门控）高是「机制存在」的证明；但「机制好不好用」还需真实用户验证
竞品数据（各项目 star、渠道数、记忆模块数）中会过时，是「公开材料归纳」；引用时标注日期
评分卡分数（8.5 / 7.6 等）主观只是我的判断，不是客观事实。看趋势，别抠小数

3.2 报告的核心结论，翻译成人话

结论一：你的技术不是问题，你的「没人知道」才是问题

报告给了工程 8.5、桌宠创新 9.0、文档诚实 9.2——这些都是「优等生」分数。但分发/生态只有 2.0。翻译：你做的东西是真的好，但现在是「深巷里的好酒」。发布要解决的是「怎么让人闻到」，不是「怎么让酒更香」。

结论二：你的 Agent 团队「设计满分、验证待补」

设计质量 8/10，验证可靠性 6/10。翻译：机制都对、代码都真，但「在真实用户手里好不好用」这件事，你自己也不知道（因为没做过可用性测试）。这不是缺点，是「诚实」——但发布文案不能说成「已验证好用」。

结论三：你唯一的护城河，是「桌宠绑定真实执行状态」

记忆、对抗评审、工具筛选这些，竞品都有或更好。真正「只有你有」的，是让干活的人自己被看见。翻译：发布的所有宣传物料，都应该围绕这一个点打，而不是列 20 个功能。

3.3 你现在要做的 3 个决策

决策一：现在发不发？

建议：发。你的功能密度已经够了，再等只会「越等越不敢发」。但先把 P0 两件小事做完（测试去 flaky + 刷新数字），约 1 天。

理由：0-star 项目的最大风险是「永远不发布」，不是「发布得不够完美」。

决策二：发布前做什么？

只做 4 件：① 测试去 flaky ② 刷新 README 数字 ③ 加 /yak /recha 手动命令 ④ Telegram 跑通录屏。约 2 天，别再多了。

理由：发布前每多花一天在功能上，都是在推迟「被人看见」这件事。

决策三：发布物料做什么？

60~90 秒演示视频（核心）+ 一份围绕「有身体的团队 Agent」的 README。视频里要演出来：你说一句话 → Yak 在后台写代码 → 桌宠在敲键盘 → 热茶挑刺 → Lumina 用人话回你。

理由：你的差异化是「体验」，体验只能用视频演，文字描述不出来。

决策四：怎么定位？

不要和 openclaw 拼渠道、不要和 N.E.K.O 拼记忆。你的位置是——「有情绪、有团队、能真正帮你干活的桌面伙伴」。抢的是「想要陪伴 + 想省事」的人，不是「要最强编码 Agent」的人。

理由：去别人的主场打仗必输；守住自己的空位才赢。

3.4 最后一句实话

我读过你仓库里的自评文档，也读过你自己抓出来的 P0 缺陷。说实话——你的「诚实」本身就是这个项目最稀缺的资产。开源圈里，把模板兜底伪装成大模型输出的项目一大堆；愿意写「这里有死代码」「这个能力我们没验证」的，极少。

发布时千万别因为「怕 star 少」而把话说满。把「已验证」和「待验证」分清楚，反而会赢得专业用户的信任——因为他们最烦的就是吹牛。你已经做对了最难的部分，剩下的只是「让人看见」。
