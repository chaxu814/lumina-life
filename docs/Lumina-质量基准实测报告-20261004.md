# Lumina 任务质量基准 v1 — 实测报告

> 采集日期：2026-10-04 · 全部通过 Lumina 自己的 REST API（localhost:3456）测真实产品链路
> 基准脚本：`.cowork-temp/quality-bench.cjs` · 原始数据：`quality-result.json`

## 为什么要有这个

之前所有验证测的都是「管道通不通」（能不能调工具、能不能委托、能不能写文件）。
那个阶段结束后，剩下的问题只有一个：**同样的管道，1.4B 和 35B 干出来的东西差多少？**

这个问题只能靠跑真实任务回答。

## 方法

五个维度，每项都有客观判据（是否真的调了某个工具 / 文件是否真的生成 / 回答里是否出现正确内容），
不靠「看起来还行」：

| 维度 | 判据 |
|---|---|
| ① 工具选择正确率 | 应用日志里是否真的出现该工具调用 |
| ② 委托判断 | 该派的派了没；不该派的有没有乱派 |
| ③ 代码产出质量 | 文件是否真生成、内容是否符合要求、能否运行 |
| ④ 审查有效性 | 能否抓到预埋的真 bug |
| ⑤ 记忆准确性 | 存进去的东西能否答对 |

## 结果对比

| 维度 | **NeoHorse-1-4B**（1.4B） | **Qwen3.6-35B-A3B**（Opus 蒸馏） |
|---|---|---|
| ① 工具选择 | **2/3** | **3/3** |
| ② 委托判断 | 1/2 | **1/2**（但见下） |
| ③ 代码产出 | **0/1** | **1/1**（文件生成且可运行） |
| ④ 审查有效性 | **1/1** | **1/1** |
| ⑤ 记忆准确性 | 1/2 | 未跑完 |
| **总分** | **5/9 (56%)** | **6/7 (86%)**（已跑完部分） |

### 关键差异一：1.4B 会「嘴上说做了」

```
任务：让它 memory_save 记住「煤球是只橘猫」
1.4B 回复：「✅ 记住了！煤煤复是只橘猫。以后聊天提到它我都知道啦～ 🐱」
     实际调用：memory_save ← 日志里根本没有
```

**它声称做了没做的事。** 这是 Lumina 宣传里要防的幻觉，而且发生在最典型的场景。

35B 同样任务：`实际调用: memory_save | 26.2s` —— 真的调了。

> 记忆**存储层**的防幻觉（权威性只由 `source` 决定）是对的，但防不住
> **模型在对话里谎称自己执行了某个动作**。这是一个此前没被识别的缺口。

### 关键差异二：代码能不能跑

| | 1.4B | 35B |
|---|---|---|
| 文件是否生成 | ❌ 完全没生成 | ✅ 生成 |
| 代码能否运行 | — | ✅ `fib.py` 实跑输出 `0 1 1 2 …` |
| 边界处理 | — | `palindrome.py` 有 keyword-only 参数、ignore_case、strip_whitespace，docstring 带 Examples |
| **运行时是否崩** | — | **❌ 崩了**（见下） |

### 关键差异三：35B 写的代码有个真实缺陷

`palindrome.py` **语法正确**（`py_compile` 通过），但**一运行就崩**：

```
UnicodeEncodeError: 'gbk' codec can't encode character '\u2705'
```

代码在 print 里用了 ✅ emoji，而 Windows 默认 GBK 控制台编码不了它。
**模型自己没测出来。** 这是 LLM 写代码的经典失败模式 —— 语法对、逻辑对、
但没在目标环境跑过。

### 关键差异四：35B 不派活了

35B 拿到「帮我写个回文函数」的任务时，**没有调 `delegate_to`**，而是
自己用了 `file_write` + `shell_exec` + `file_search`（耗时 307.6s）直接干完。

```
实际调用: file_write, shell_exec, file_search
```

原因大概�� Lumina 自己就有这些工具（`agent` 模式 56 个，含 `file_write`/`shell_exec`），
而模型判断「我自己能做完」。

**这是产品设计问题，不是模型问题** —— 如果「三 Agent 团队」是卖点，
那 Lumina 手里就不该同时握着全套写代码的工具，否则团队永远派不上用场。
工具分档设计上，`agent` 档应该把「写文件/跑命令」这类**执行**能力留给 worker，
Lumina 只保留「派活 + 复核」。当前设计让最强的模型绕过团队，这削弱了差异化。

### 关键差异五：审查能力两个模型都不差

| 模型 | 表现 |
|---|---|
| 1.4B | 抓到 `ZeroDivisionError`，给了行号，**还额外找出缺类型校验 → TypeError**，按严重度列表 |
| 35B | 抓到 `ZeroDivisionError`，给出修法代码，指出 `total = 0` 可改 `sum()`，并说明「但这属于输入校验范畴」 |

**审查是五个维度里两个模型都做好的。** 这可能说明「代码审查」对 LLM 来说是
相对容易的任务 —— 挑错比动手写容易。

## 顺带发现的三个工程问题

### ① `file_search` 没有路径作用域限制

日志显示它在逐盘扫描：

```
[fileSearch] C:\: 1 结果, 63806ms
[fileSearch] D:\: 0 结果, 677ms
[fileSearch] E:\: 0 结果, 446ms
[fileSearch] F:\: 0 结果, 15049ms
[fileSearch] J:\: 0 结果, 16180ms
```

**扫完整个 C 盘花了 63.8 秒。** 用户如果没给路径，一次 `file_search`
可能让对话卡住一分钟以上。这是明确的体验问题。

### ② 沙箱重定向把 Windows 盘符路径写坏了

```
期望：D:\lumina-quality\fib.py
实际：C:\Users\13510\Lumina\sandbox\lumina\Dlumina-quality\fib.py
                                  ↑↑↑↑↑ 冒号+反斜杠被吃掉，变成 "Dlumina-quality"
```

沙箱把写入重定向到 `<userData>/sandbox/lumina/` 下，这个设计本身没问题，
但**路径拼接时 `:\` 被替换掉了**，导致目录名变成 `Dlumina-quality`。
后果是用户按提示去原路径找文件会找不到。

### ③ 我的基准脚本本身也犯了同类错误

`toolsSince()` 原本用「往日志里写一个 MARK 字符串」做分界，
但那个 MARK 从来没真写进去，于是函数永远返回空 ——
**明明日志里写着 `收到工具调用: memory_save`，基准却报「没调工具」。**

> 教训：**测试工具的静默失败会被误读成「被测系统失败」**，比没有测试更危险。
> 改成按字节偏移切分日志后才拿到正确数据。
> 这与项目里那个「恒等于 0 的孤儿守卫」是同一类错误 —— 我在这轮里犯过两次。

## 结论

### 能下的结论

1. **模型选择对 Lumina 的影响是决定性的**：同样的管道，1.4B 得 56%、
   35B 已跑部分 86%。**Lumina 的能力下限完全由所配模型决定**，框架本身
   提供的差异化（团队编排、沙箱、记忆、主动性）只有在模型够强时才体现出来。

2. **35B + Lumina 能写出可运行的代码**：`fib.py` 实跑通过，
   `palindrome.py` 结构良好但有 Windows 编码问题。**约 1/2 一次通过。**

3. **审查能力两个模型都可用**，且都能超额发现问题。

4. **发现一个此前没识别的幻觉缺口**：模型会在对话里谎称自己执行了工具调用。
   记忆层的防幻觉管不了这个。

5. **发现一个削弱核心卖点的设计问题**：Lumina 自己握着全套执行工具，
   导致强模型绕过团队自己干 —— 「三 Agent 团队」这个卖点在强模型下会被架空。

### 不能下的结论

- **样本太小**（9 项，35B 只跑完 7 项），不足以支撑「Lumina 质量如何」的整体判断
- **没测过真正复杂的任务**：真实代码重构、多轮修复、需要理解大型代码库的活
- **没测过对抗评审 / 五阶段门控的质量**（这两条链路要跑完整编排，
  35B 每次几分钟，本轮没跑完）
- **没有对照基线**：不知道 Claude Code / cursor 在同样任务上是什么水平

### 建议的下一步

1. **给 `file_search` 加默认路径作用域**（当前项目目录），避免全盘扫描
2. **修沙箱的 Windows 盘符路径拼接**（`D:\x` → `Dlumina-quality`）
3. **考虑收窄 `agent` 档的执行类工具**，让「派活给 Yak」成为默认路径而非可选
4. **加大基准**：每个维度至少 5 个样本，加真实复杂任务，与外部工具做对照
