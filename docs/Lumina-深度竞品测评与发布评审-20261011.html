02Lumina 是什么：架构解剖

进程模型是经典 Electron 三段式：主进程（全部 Agent 逻辑与工具执行）→ IPC → 渲染进程（面板 UI），另加桌宠独立多窗口。主进程承载全部「智能」，渲染进程基本是壳——这对安全有利（工具不在渲染进程执行，攻击面更小）。

2.2 一次请求的完整数据流

用户输入 → 工具路由 toolRouter（按语义从 138 个里挑 31~45 个暴露给模型） → 路由仲裁 routingDecider（规则高置信直接定 / 歧义调一次 LLM / 失败静默退回） → AgentRunner ReAct 主循环（maxRounds=30，防空转） → [可选] 委托 Yak / 热茶 / 动态雇工 → 对抗评审 → 验证闭环 → 角色闸门 rolePolicy（deny 优先，执行层 + 广告层双重过滤） → 情绪门控 emotionGating（只能收紧，永不放宽） → 记忆写入 / 召回（source 决定权威性 + 五维证据排序） → Lumina 整理成人话 → 用户（只看到 Lumina）

2.3 设计上的一个亮点：工具按需筛选

修复前每轮把整档工具全量塞进 function list——agent 档 9,710 tokens、developer 档 12,075 tokens，每次模型调用都重发一遍（包括问「现在几点」）。现在 toolRouter.ts 按你这句话挑相关子集，每轮 5,495 tokens 起，能力一个没少。这是一个真实且正确的工程优化，README 里有完整的前后对照。

03Agent 与团队 Agent 质量深评 核心

这是你最关心的问题。结论先给：Lumina 的 Agent 团队是真的，机制设计水平高于它的社区体量两个数量级；但它有一个「不可预测性」的原生缺陷，必须如实认知。

3.1 三个 Agent 与「铁则」

Agent角色对用户可见工具边界职责
Lumina 🐱boss✅ 唯一入口全量放行对话 · 情绪 · 派活 · 整理结果
Yak 💻worker❌ 隐身可写 / 可执行 / 可提交（白名单 30+）写码 · 调 bug · 重构 · 跑测试
热茶 🍵worker❌ 隐身只读（显式 deny 写 / 执行 / 提交）审查 · 挑错 · 风险评估

三条铁则：① 用户只跟 Lumina 说话；② Worker 不主动跟用户说话、不直接返回结果；③ Worker 之间不直接对话，通信经 Lumina 转发。这是「单入口 + 隐身团队」的产品判断，与 openclaw 的「多 session 各自可见」、cc-haha 的「泳道可视化」是不同路线。

3.2 逐个机制的质量判定（我逐文件核对过）

① 角色权限闸门 rolePolicy.ts —— 单一事实源，优秀

  • deny 优先：显式拒绝优先级最高，即使误入 allow 也一律拒绝。
  • fail-closed：传入的全量工具清单为空时，绝不返回空 deny 悄悄放行，而是退回静态 denylist——保证受限角色仍被禁用。这是一个真正的安全设计（防「静默提权」）。
  • 别名解析：历史配置写的是语义别名（write_code），运行时先解析成真实工具名（file_write）再判定，避免历史配置被误判。
  • 广告层 + 执行层双重调用：不只过滤给模型看的工具清单，reactEngine 硬闸门在真正执行前再查一次。这是「不信任模型自觉」的正确姿势。

② 路由仲裁 routingDecider.ts —— 三档降级，设计优秀 但本质是建议

  • 三档：规则高置信直接定（零延迟零成本）→ 歧义才调一次 LLM（1.2s 硬超时，fire-and-forget 预热缓存）→ LLM 失败 / 超时 / 返回垃圾 → 静默退回规则默认。任何一环失败都不让用户卡住。
  • 处理了两个经典失败模式：漏派（「这玩意跑起来就崩，你帮我看看」无关键词）和错派（「解释一下这段 JSON 的 algorithm 字段」是纯答疑）。
  • 先判「这句话是不是没头没尾」（clarifyScope），模糊任务优先要澄清而非硬派——这是很多 Agent 产品没做的。
  • ⚠️ 关键真相：终点是一句注入 system prompt 的提示语，不是确定性派活。派不派、派给谁，最终由模型读完 prompt 后自己判断。好处是灵活、不会误路由；代价是同一问题两次问，可能一次派给 Yak、一次 Lumina 自己答。这是全项目最需要向用户如实说明的一点。

③ 对抗式评审 adversarialReview.ts —— 并发多视角，优秀

  • 用 Promise.all 并发委托多视角（正确性 / 安全 / 可复现），每个怀疑者输出 JSON 判定（verdict / severity / findings）。
  • 多数票 + 高危一票否决，再上「完整性批评员」专查评审本身漏掉了什么（没测的边界、没考虑的回滚、缺失的验收步骤）。
  • JSON 解析失败会退化为文本启发式判定（不因格式问题丢结论）；热茶未配置时自动雇临时复核员兜底。
  • 把「亲密度 → 审查语气」真正接在了这里（reviewTonePrompt()）——注释里明说「以前写好了却没人调用，属于文档吹了、代码没接」，现在接通了。

④ 五阶段门控 phaseGate.ts —— Research→Plan→Execute→Verify→Review，良好

  • 每阶段有明确准入条件（checkGate），阶段间通过任务看板传递产物，支持动态跳过与并行批次。
  • 关键阶段（execute / verify）失败即终止后续，不硬撑。
  • 自动降级：简单任务自动降级为一次普通 delegate_to，避免「杀鸡用牛刀」。
  • 修复了历史角色映射错误（调研/执行/验证曾挂给只读的热茶，导致门控形同虚设）。

⑤ 情绪门控 emotionGating.ts —— 情绪进执行层，创新点

这是全项目最有想法的设计之一，核心是一条安全约束：情绪只能「收紧」工具，绝不能「放开」。

为什么重要：如果「开心时解锁更多工具」，那么「诱导她开心」就变成了「解锁更多权限」的社工攻击面——从对话层攻击到执行层。收紧方向则是安全的：情绪低落时少接重活，最坏结果是「这轮没做完」，用户再问一次即可。

三个策略：① 焦虑高 + 情绪不稳 → 暂缓不可逆操作（删文件/发邮件/git push/桌面操控）；② 疲劳高 → 暂缓重活；③ 好奇高 → 刻意什么都不做（如果拿好奇心解锁能力，就违反了整个模块的安全前提）。

⑥ 动态雇工 + 隔离 + 模型分层 team/ —— 优秀

  • 7 工种（research/search/data/code/review/test/general）当场雇佣、并行执行、干完即散。
  • code worker 自动开 git worktree 隔离，成功自动合并、失败保留现场——这是工程化 Agent 的成熟做法。
  • 杂活工种自动换便宜模型（modelTier.ts）——成本控制意识。
  • 全局并发帽默认 2（可调 1~8），刻意保守，避免常驻桌宠夜间烧 token。

3.3 团队 Agent 整体质量判定

强项（真实、可测）

  • 独立 Runner 实例，不是同一 prompt 换皮
  • 权限闸门是「单一事实源 + deny 优先 + fail-closed」，安全姿势正确
  • 对抗评审是真并发 + 多数票 + 高危否决 + 完整性批评，比单次委托严格得多
  • 编排能力丰富：门控 / 雇工 / 任务板 / 信箱 / 快照 / 日报 / 泳道
  • 弱模型自动降级（≤7B 进轻量模式，砍掉危险工具）
  • 反幻觉落地：空产出强制转失败、UI 标注「来源: llm / template」

弱项（必须如实认知）

  • 不可预测：路由/编排触发依赖模型自觉，无确定性调度器
  • agentRunner.ts 4285 行单体，外部贡献者可读性差
  • 约 5100 条 no-explicit-any warning（棘轮管理，只减不增）
  • 测试套件对负载敏感，慢机/并发下个别时序测试会间歇失败
  • 五阶段门控 / 对抗评审未经真实任务充分验证（作者自己标注）
  • 人格厚度：每人 55~75 行身份文件 vs N.E.K.O 的 persona/ 8 模块

我的判定：Agent 团队的「设计质量」是 8/10，「经过验证的可靠性」是 6/10。差距在于——机制都对，但大部分编排路径只有测试和作者自测覆盖，没有真实用户数据。发布时如果把这两者混为一谈（把「设计得好」说成「验证过好用」），会在 issue 区被拆穿。建议 README 明确写「编排能力丰富，但触发依赖模型裁量、未经大规模真实任务验证」。（好消息：项目已有自评文档在这么做。）

4.1 🔴 N.E.K.O —— 唯一真正的直接对手

形态

4.3 🔵 openclaw —— 别当对手，当上游

形态

5.2 Lumina 的竞争优势（按可持续性排序）

🥇 桌宠绑定真实 Agent 执行状态 —— 唯一的护城河

这是 5 个对标项目里唯一一个「让干活的人自己被看见」的。Yak 写代码 → 敲键盘循环 + 专注光晕；热茶审查 → 审视表情 + 怀疑色；验证失败 → 捂脸/黯淡。零 LLM 调用（纯状态机映射），1.2s 防抖，空闲不接管。

对照：cc-haha 作者自己写明其桌宠「只是个状态提示和跳转入口，不能替你批准权限」；AIRI 的表情来自模型输出但不绑定真实执行状态。Lumina 恰好越过了这条线——审查员真的在审查代码产出。

🥈 情绪参与系统决策（而非只换表情）

delegationManager 里情绪影响重试次数；emotionGating 让情绪参与工具收紧（且只能收紧不能放宽）。多数项目的「情绪系统」只是换头像和语气词，Lumina 让它进了执行层。

🥉 「用户只看到一个 Lumina」的隐藏编排

后台三 Agent 协作，用户全程不知道。对比 openclaw 的多渠道多 session（用户要自己管理 session 概念），这是不同的产品判断——把复杂度留给自己，把简单留给用户。

🏅 反幻觉的工程化落地

  • 记忆权威性只由 source 决定，模型无权自封 confidence: 1.0
  • worker 只调工具不下结论的空产出强制转失败（防「空信封 → 主模型自己编一个结论」）
  • UI 标注 来源: llm / 来源: template，绝不假装是大模型写的

最后一条在开源项目里极其稀缺——大量项目把模板兜底伪装成 AI 输出。

⑤ 8×9 精灵表 UGC：把做桌宠的门槛降下来

Live2D/VRM 需要会 Blender、会绑 3D 模型。精灵表把门槛从「掌握 Blender」降到「会跟 AI 画画的普通人」：三条创建路径（单张静态图 1 分钟 / 提示词 10 分钟 / 已有图集导入），全程本地处理不消耗模型额度，有校验器。
