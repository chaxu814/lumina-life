## 0.5 ⚠️ 勘误（2026-10-02 晚，修复实施后复查发现）

**本报告初版的以下两条结论是错的，原因是首轮只探针了确定性模块，没有深挖 agent 主循环。修复过程中核对源码后确认：**

| 初版结论 | 实际情况 | 证据 |
|---------|---------|------|
| ❌「委派路由是 `shouldDelegateToYak()` 正则匹配，非 LLM 判定」 | **错的。** 真实委派是 **LLM 自主决策**：system prompt（AGENTS.md）内置委派规则 + 团队状态表，模型自己决定何时调 `delegate_to` 工具。`shouldDelegateToYak/shouldDelegateToRecha` 这两个函数**全仓无任何调用点**，是遗留的未使用代码。 | 全仓 `git ls-files` 全文搜索仅命中定义处 `electron/prompts/systemPrompt.ts` |
| ❌「长任务无硬性迭代上限，收敛控制有失控风险」 | **错的。** `runReActLoop` 已有硬性上限 `maxRounds = config.maxToolCalls ?? 30`，外加**两道安全门**：① 同工具重复≥5 次 → 注入停止提示 + 封禁该工具 2 轮；② 总工具调用 >30 → 强制收敛（且用 `converged` 标记防重复触发）。另有 `_autoContinueCount` 与意图句式 hash 双重死循环检测。 | `electron/agentRunner.ts:1813-1855` |

**这两条错误低估了 Lumina 的 agent 工程质量**，而用户正准备据此发布。请以本节为准。

**修正后的评价：** 委派决策 6/10 → **7.5/10**（LLM 自主决策本身就是更好的设计；扣分点在于「模型可能忘记委派」，已通过路由先验提示缓解）；收敛控制 6/10 → **8.5/10**（三重复核机制，设计扎实）。综合分由 7.4 调整为 **7.8/10**。

**因此「§7.2 做不到的事」列表应删除以下两条：**

## 0.8 第二轮新增：决策卡片 + 子智能体卡片

用户看完第一轮后提出两个设计借鉴需求，均已实现。

### 🧭 决策卡片（图1 借鉴）—— `ask_decision`

**核心设计判断：必须与 `approvalService` 严格分离。** 这是本轮最关键的决定。

| | 审批 approvalService（已有） | 决策 ask_decision（新增） |
|---|---|---|
| 问什么 | 「我可以做 X 吗」 | 「你想走哪条路」 |
| 目的 | 安全闸门 | 协作对齐 |
| 形态 | 二值（同意/拒绝） | N 选项 + 自由输入 |
| 不回答后果 | **操作被拦下** | **按推荐项继续** |
| 触发方 | 系统检测到高风险工具 | agent 遇到分叉点 |

一句话：**审批是刹车，决策是问路。刹车坏了会撞人，问路坏了只是走错路。** 混在一起会导致「用户不答 → agent 永久卡死」。

**实现**
- `electron/decisionService.ts` — 决策中枢（校验/超时/并发上限/默认兜底/摘要生成）
- `electron/tools/impl/askDecision.ts` — agent 的提问出口（工具名 `ask_decision`）
- `src/components/DecisionCard.tsx` + `src/styles/decision-card.css` — 卡片 UI
- IPC 接线 + preload API + ChatPanel 挂载

**「绝不阻塞 agent」的六道防线**（每一道都有测试钉死）
1. 开关关闭 → 立即默认
2. 参数非法 → 立即返回错误让 agent 自纠
3. 挂起数超上限 → 立即默认（防 agent 疯狂提问刷屏）
4. 无 UI 订阅者 → 立即默认
5. 超时（默认 5 分钟）→ 按推荐项继续
6. 工具层 try/catch 兜底 → 即使决策系统崩溃也返回「没问到，请自行决定」

**设计细节**
- 推荐项**默认预选**，用户点「确定」即可
- 自由输入框是**一等公民**（与选项同级）——用户常觉得选项都不对，打字更快
- 卡片显示倒计时，让用户知道「不回答会自动继续」而不是干等
- Enter 提交 / Shift+Enter 换行
- `prefers-reduced-motion` 降级

**测试：34 条**，重心全在异常路径。

### 0.7 修复过程中额外挖出的 3 个真实 bug

这些不在初版报告里，是实施修复时翻代码发现的：

**① 新闻推送时段配置完全失效（用户可见，影响大）**
`newsDigestScheduler.checkAndPush()` 里写死了 `if (![8,12,18,22].includes(slot)) return`，

这类 bug 很危险：UI 上选项能改、能保存，但行为永远不变，用户只会觉得“这软件没生效”。已修。

**② `runSubagents` 派生时 owner 固定为 `yak`**
`internPool` 的 v3.0 支持 `owner: lumina | yak | recha`（子智能体权限继承 owner），

你问的「三个主智能体都能派生子智能体吗」——能力有，**默认值没跟上**。

**③ 路由兜底可能派给未配置的 agent**
`routingDecider` 编写过程中我自己引入又修掉的问题（fallback 写死 `'yak'`，
在只配了 lumina+recha 的场景会把任务派给不存在的成员，任务石沉大海）。
写成测试用例固定住了。

## 3. Lumina 的真实优势（按含金量排序）

### 🥇 优势 1：情绪不是贴图，是有物理规律的连续系统

README 写「五维 + 三维情绪」，代码里的实现比这更扎实：`mood/energy/affinity` 三个连续数值，带**惯性、随机漂移、昼夜节律**。更关键的是它**反向影响行为**而不只是影响表情：

- 情绪被注入 system prompt，附带**可执行的风格指令**（不是"你现在开心"这种废话，而是"语气轻快活泼，多用感叹号"）
- 委托失败重试策略随情绪变化：好心情 → 多试几次；疲惫 → 尽快出结果；不耐烦 → 几乎不重试
- 代码里有一条我特别认可的自省注释：情绪低落时「但如果用户在求助/问正经问题，**忽略'简洁安静'，给出完整有耐心的回答**」

**没有任何一个对手做到情绪参与 agent 决策。** N.E.K.O 有 trust/persona 演进，AIRI 的 core-character 只有 index.ts。这是 Lumina 真正不可复制的深度。

### 🥈 优势 2：AI 表演 DSL —— 让 LLM 指挥身体而不是逐帧刷参数

`electron/pet/life/performanceDsl.ts` 是一个教科书级的设计。设计者面对的问题是：让 LLM 直接输出 100+ 帧参数 = 贵 + 不稳 + 会鬼畜 + 可能触发魔法特效。

解法是分层：
```
LLM 输出高层意图 → {expression, gaze, gesture, headTilt, motion, effect, durationMs, blend}
                        ↓
        白名单校验 + 数值钳制（gesture 19 种白名单 / effect 8 种白名单）
                        ↓
              NormalizedPerformance（类型安全）
                        ↓
                   渲染层执行
```
非法项**丢弃并记录 errors，绝不抛穿**。这解决了我见过的几乎所有「LLM 驱动角色」项目的通病。

### 🥉 优势 3：自研的 Agent 质量闭环（对手要么没有，要么是继承的）

这是你被低估最严重的地方。`electron/orchestration/` + `electron/team/` 里有一整套 cc-haha 完全没有的东西：

- **`verifyLoop.ts`** — Yak 写完代码自动跑 tsc/vitest，失败则生成带错误日志的修复任务重委托，**最多 3 轮**，只有 Yak 有写权限（热茶只读）。这是真正的自我修复闭环。
- **`complexityAnalyzer.ts`** — 任务打分，≥50 分自动切分 research/plan/execute/review/verify 阶段
- **`phaseGate.ts`（18.7KB）** — 阶段门控
- **`adversarialReview.ts`** — 对抗式审查
- **`internPool.ts`（18.9KB）** — 实习生池，hire→busy→done/fail 状态机，带状态校验
- **`gitWorktree.ts`** — 真实 git worktree 隔离并发
- **`workerStats.ts` / `teamSharedBoard.ts` / `workflowScript.ts`** — 任务看板、动态工作流脚本
- **`llmTrace.ts`** — 每次 LLM 调用可追溯

**对照组**：cc-haha 是 Claude Code 的 GUI 壳，agent 循环完全继承；N.E.K.O 是单执行器没有编排；AIRI 多 agent「未成体系」。**在「多 agent 协作的工程深度」这一项上，Lumina 是全场唯一自研且成体系的。**

### 优势 4：安全是真的

26 条沙箱规则（已核实）+ `securityGuard` 五级 CRITICAL/HIGH/MEDIUM/LOW/INFO + 沙箱玻璃房可视化 + 审批流 + 注入净化 + 密钥拦截。对比 N.E.K.O 的未鉴权端点，这是代差。

## 4. Lumina 的真实劣势（必须诚实面对）

### ⚠️ 劣势 1：README 存在功能虚标 —— 首发最大信誉风险

| 声明 | 实测 |
|------|------|
| 「BM25 + TF-IDF 双路召回，**RRF 融合（已实现）**」 | ❌ **全仓 0 处 RRF**。两套独立实现未融合 |

### ⚠️ 劣势 2：复杂度分析器的失效模式打在了最危险的场景

「重构整个项目的架构，全面优化」被判为 simple（25 < 50）。这正是最该走 plan→execute→review→verify 全流程的任务。根因是正则权重表没有去重计分、且阈值过于武断。**建议：让 LLM 参与复杂度判定（确定性正则降级为预筛），或至少把「重构/重构整个」提到 40+ 并对多信号命中做平方加成。**

### ⚠️ 劣势 3：`agentRunner.ts` 166KB 单体文件

从 v9.3 → v10.0 → v16.0 的层层补丁痕迹清晰可见（「防 isIntentOnly 死循环」「上一轮意图句式 hash」「去重：history 末尾 user 消息与 sendMessage 重复」）。这说明**系统是在真实使用中被反复打磨的**（是好事），但也说明它已经需要一次拆分：ReAct 循环、工具调用解析、搜索预处理、持久化各自分离。开源后社区第一个 PR 大概率就是「拆分 agentRunner」，你不主动拆会显得不欢迎贡献。

### ⚠️ 劣势 4：跨平台是「配置就绪」而非「验证通过」

package.json 里 mac(dmg+zip) / linux(AppImage+deb) 都配好了，CI 也配了，但 README 自己写「当前 v0.1.0-preview **仅支持 Windows 10/11**」。Computer Use 的键鼠注入、UIA、沙箱规则、托盘全部深度依赖 Windows API。**这是合理的取舍，但要确保 README 和 Release Notes 措辞一致，别让用户装 Linux 版后开箱即坏。**

### ⚠️ 劣势 5：对手的规模效应不可撼动

openclaw 391k star / 82.2k fork / 每 2-3 天一版 / 9.2k open issues（积压）。N.E.K.O 单个 `facts.py` 就 294KB 但有 3019 个 PR、65 位贡献者。**Lumina 是单人/小团队项目，永远不要在「生态规模」这个维度上正面比较。** 你的 README 现在的对比表把 Lumina 和这些项目并排比较，暗示「别人没有我有」，这个策略在面对 391k star 的平台时会显得傲慢且不自量力。**建议改成「我适合谁 / 我不适合谁」的定位式表述。**

**不能。** 但比大多数人预期的强。

### 给「问什么就解决什么」这个目标的实话

3. Lumina 自身的工程优化（已做得比较到位，继续挖的边际收益在下降）

这两处是**项目根目录探测的降级兜底**。对陌生用户毫无意义（他们的机器上不存在 `J:\LuminaLife2.0`），只会让人觉得是私人项目的遗留。**建议直接删除这两个降级分支**（前面的 `app.getAppPath()` / `process.cwd()` / `LUMINA_PROJECT_ROOT` 环境变量已经足够覆盖），或在首次启动时写入 `LUMINA_PROJECT_ROOT` 后完全依赖环境变量。

其余 10 个文件（`SettingsPanel.tsx` / `SettingsTTS.tsx` / 测试 fixture / 文档示例）大多是注释和默认值，风险低，但建议一并清理。
