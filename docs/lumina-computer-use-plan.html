Computer Use 视觉 Agent：cc-haha 对标 × Lumina 现状 × 增强路线
2026-09-16 ｜ 本轮已落地：桌宠窗口占位优化（本地 commit 68a1fb3）｜ 结论：你不是从零开始，已有两套闭环骨架，真正卡脖子的是“看得准、接得上、点得对、管得住”四件事。
一眼结论：cc-haha 的 Computer Use 本质是 “截图 → 强视觉模型直接读坐标 → 人工确认 → pyautogui 执行 → 再截图验证” 的循环，强在动作原语全（24 个工具）+ 白名单/权限严 + Mac 另有原生无障碍树深度方案；需注意 Windows 其实也已全支持（win32 栈），最深的 AX/JS 方案为 Mac 专属，且源码有合规灰区。Lumina 已具备同款循环（desktop_see / desktop_act，含点击/双击/右键/拖拽/滚动 + 审批门），但目前 ① 让小模型裸估坐标（点不准）② 设置里的模型没接进去（开箱即失败）③ 高分屏 DPI 与中文输入没处理 ④ 失败即停、缺验证与急停。
① cc-haha 的 Computer Use 是怎么跑起来的
🖱 动作原语（很全）
screenshot / zoom；click、drag、move、scroll、读光标；type、press、hold；打开应用、切显示器；剪贴板读写；wait、batch。
🧱 双轨底层（关键）
通用轨：Python bridge（pyautogui/mss，Mac 用 pyobjc、Win 用 win32gui/psutil/pyperclip/screeninfo），Mac+Win 都全支持。Mac 原生深度轨：编译型 Swift cu-helper，读无障碍元素树(AX)+截图双通道、持久 JS 执行器、元素句柄，对标 OpenAI Codex（Windows 仍只是像素轨）。
🔐 平台与权限
macOS 全支持（需辅助功能+屏幕录制）；Windows x64 也全支持（win32gui/psutil，免额外系统授权）；Linux 未适配。安全：应用白名单、并发文件锁（同时只一个会话操控）、系统快捷键额外门、剪贴板守卫。
⚠️ 合规灰区（别照抄）
自述基于 2026-03-31 泄露的 Claude Code 源码（版权归 Anthropic，仅学习研究），并用 LiteLLM 代理转第三方模型。Lumina 只借鉴“工具范式与交互”，不抄源码、不走灰色代理。

④ 为什么现在“不够强”：四个卡脖子命门
命门 1 · 看得准吗
小模型裸眼估坐标天然不准。cc-haha 能成立是因为背后是 Claude 级视觉。解法是 Set-of-Mark：在截图上给可点元素画编号/网格，让模型“选编号”而不是“猜像素”，必要时 zoom 放大再点。
命门 2 · 接得上吗
设置里明明配了模型，CU 却只读环境变量。必须把 desktop_act / desktop_see 的 VLM 配置回退到设置中的 brain config（复用 resolvePetBrainConfig / 设置 store），否则功能对普通用户等于不存在。
命门 3 · 点得对吗
高分屏（125%/150% 缩放）截图坐标与鼠标坐标不一致会系统性点偏；Windows SendKeys 输不了中文。要做 scaleFactor 换算 + 剪贴板粘贴输入（需真机截一张图量分辨率校准）。
命门 4 · 管得住吗
AI 操控真实桌面是高风险能力。需要动作预览（截图上画出要点哪）、全局急停、应用白/黑名单、敏感区域避让、操作审计；并修掉 IPC 那套“无回调默认放行”。
⑤ 增强路线（建议顺序）
P0 · 让它“开箱能跑、点得准”
  1. CU 的 VLM 配置复用设置中的模型（去掉只认 env 的断裂）
  2. Set-of-Mark 标注：截图叠加编号网格/候选框，模型回编号→映射坐标（纯 TS 可单测）
  3. 坐标改归一化 0–100（模型出相对坐标、引擎映射实屏，免疫分辨率/DPI，低成本高收益）
  4. Windows 输入改剪贴板粘贴，修中文
  5. 修 IPC 套“默认放行”，统一走审批门
验收：一句“打开记事本写一句你好”在本地模型下端到端成功。
P1 · 让它“稳、可控”
  1. 动作后截图验证 + 画面变化检测，失败有限重试/换策略
  2. zoom 局部放大二次定位（小元素/高密度 UI）
  3. 补 hover、修饰键组合（Ctrl/Shift+点击）、长按、读光标
  4. 动作预览高亮 + 全局急停（Esc/快捷键）+ 操作日志
  5. 桌宠猫爪提示词放开视觉 click，并把当前屏截图喂给意图模型
验收：连续 5 步任务不卡死，危险动作必停。
P2 · 让它“有 Lumina 灵魂”
  1. 宠物化操作反馈：眼睛/头看向点击处、伸手手势、边操作边语音解说、成败表情
  2. 结合记忆：记住常用软件/账号入口/操作习惯，主动代办
  3. 多显示器、按应用切换、应用白名单
  4. 可选执行层升级 nut.js（纯 Node 原生，免 Python/PS），评估包体与 ABI
  5. 合并两套 CU 为单一权威实现，删冗余 IPC 路径
  6. Windows 差异化（cc-haha 在 Win 都没做）：接 UI Automation 元素树——能读树就点元素句柄（不靠像素、不吃 VLM 眼神），浏览器/自绘 UI/游戏再回退截图视觉坐标
验收：像“会用电脑的小生物”，而非冷冰冰的脚本。
⑥ 开工前需要你拍板的 3 件事
决策 1 · 视觉模型路线（最关键，决定要不要重注 Set-of-Mark）：
（A）本地优先 / 隐私：继续用本地 QwenPaw 9B，我重注 Set-of-Mark + zoom 把坐标命中率拉上来（零额外费用，但准确率上限有限、复杂网页仍会错）；
（B）效果优先：CU 视觉这一环单独走强视觉云模型（如 Qwen2.5-VL / GPT-4o 类），本地模型负责对话，混合路由（准、但有费用与截图上云的隐私考量）；
（C）专门的 GUI 模型（UI-TARS 类）自托管。
决策 2 · 输入执行层：维持零依赖 PowerShell（稳但笨、中文要走剪贴板），还是引入 nut.js 原生绑定（快、可靠、跨平台，但新增原生依赖，可能踩和 better-sqlite3 类似的 ABI/打包坑）？
决策 3 · 默认权限姿态：CU 默认关闭、每次动作都问（最安全）；还是“只读观察默认开、点击/输入逐次确认、高危永久禁”分级默认开？
