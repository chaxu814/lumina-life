## 二、提案逐节评估

---

### 提案 1：Live2D 配件商城（Workshop + 分成）

#### 一句话定位

让用户在 Lumina 内浏览、下载、上传 Live2D 模型、皮肤替换、动作包和表情扩展，平台从中抽成（类似 Steam Workshop 或 Figma Community），解决"桌宠皮太少、模型安装麻烦"的问题。

#### 可行性评估：**中**

**理由：**
- **技术成熟度高**：Live2D Cubism 4/5 的模型加载管线已经跑通（当前用的虹色 Mao 模型），`pixi-live2d-display` 库支持热切换 model3.json。技术上"换皮"是成熟能力。
- **但商城是系统工程**：需要后端存储（对象存储 CDN）、用户上传审核、版权过滤、支付结算、分成对账——这是一整套 SaaS 基础设施，不是桌面端能独立完成的。
- **依赖条件**：需要有一个云端服务（哪怕是轻量的 Supabase/CF Workers + R2），以及支付渠道（微信支付/支付宝的商户号申请周期 2-4 周）。

#### 技术要点

**核心实现思路：**

1. **客户端侧（已有基础可复用）**：
   - 当前 Live2D 模型路径在 `petWindow.ts` 中通过 URL 参数加载（`pet.html?model=Mao%2Fmao_pro.model3.json`），扩展为"从本地用户数据目录加载任意 model3.json"即可。
   - 模型包结构约定：
     ```
     ~/.lumina/pet-models/<model-id>/
     ├── model3.json
     ├── motions/*.mtn
     ├── expressions/*.exp3.json
     └── textures/*.png
     ```
   - 切换模型 = 重新加载 `pixi-live2d-display` 的 Model 对象，销毁旧实例。

2. **商城前端**：
   - 在现有 UI 面板（`src/panels/`）新增"配件商店"面板，复用现有的面板框架和 i18n。
   - 列表页：模型缩略图 + 名称 + 作者 + 下载量；详情页：Live2D 预览（用轻量 iframe 或 WebView 加载渲染 demo）+ 动作试穿 + 下载按钮。

3. **后端（轻量起步）**：
   - **MVP 阶段**：用 Cloudflare R2 存模型文件 + CF Workers 做 API（列表、上传、下载统计），零服务器运维成本。
   - **计费阶段**：接微信支付/支付宝 SDK，分成比例建议 70/30（开发者 70%，平台 30%）。
   - **审核**：UGC 上传必须有人工审核 + 自动扫描（检查 model3.json 是否内嵌恶意 JS——Cubism 支持脚本扩展）。

**关键技术选型：**
- 存储：Cloudflare R2（无 egress 费用，适合大文件分发）
- CDN：R2 自带全球边缘节点
- 后端 API：Cloudflare Workers（免费额度够用早期）
- 模型校验：写一个 Node.js 脚本校验 model3.json schema + 扫描 .mtn/.exp3.json 中是否有异常字段

**需要配合的现有模块：**
- `electron/pet/petWindow.ts` — 扩展模型加载逻辑，支持从用户目录动态加载
- `src/panels/` — 新增配件商店面板
- `electron/skills/` — 可以做一个"模型管理"技能，让 Agent 也能推荐/切换模型

#### 风险与挑战

| 风险类型 | 具体问题 | 严重度 |
|----------|----------|--------|
| **版权风险** | Live2D 模型的版权是大坑——Cubism Editor 导出的模型有用户授权，但第三方上传的模型可能是盗用的同人作品（如未经授权的原神/明日方舟角色）。一旦商用分成，版权方可能发律师函。 | 🔴 高 |
| **技术风险** | 不同模型的参数集不同（Mao 的 ParamAngleX 在别的模型上可能叫别的名字），换皮后动作映射可能错位。需要做参数自动适配或强制要求"标准动作集"。 | 🟡 中 |
| **合规风险** | 涉及 UGC 内容审核 + 支付，需要 ICP 备案、网络文化经营许可证（如果涉及虚拟道具交易）。国内合规门槛不低。 | 🔴 高 |
| **用户体验风险** | 下载的模型体积大（通常 50-200MB），首次加载慢；低端电脑加载复杂模型可能掉帧。需要预览缩略图 + 懒加载。 | 🟡 中 |

**版权问题的诚实评估**：这是整个提案最大的坑。Steam Workshop 能做是因为它有 Valve 的法务团队 + DMCA 快速下架机制。Lumina 早期建议**先做"免费分享"（不涉及金钱分成），只做模型索引和下载，不碰支付**，把版权风险降到最低。分成模式等有了用户基数和法务能力再上。

#### 优先级建议：**P2（v0.3）**

**理由：**
- v0.2 阶段用户量小，做商城的 ROI 极低（没有流量就没有创作者，没有创作者就没有内容）。
- 先在 v0.2 把"支持自定义模型路径"这个基础能力做了（开放本地加载任意 Live2D 模型），让极客用户先玩起来。
- v0.3 再考虑做线上索引和分享，v0.4 以后再考虑分成。
- 版权和合规问题需要提前做法律调研，不能仓促上线。

#### 与竞品对比

| 竞品 | 类似能力 | Lumina 差异化机会 |
|------|----------|-------------------|
| **N.E.K.O** | 有内置模型切换，但无官方商城，社区靠 Discord 分发 | 我们的优势是可以把"模型 + 动作包 + 人格 prompt"打包成一体下载——别家只有皮，我们连性格一起换 |
| **AIRI** | 支持自定义 Live2D/VRM 模型，但纯本地手动导入，无在线商店 | 我们可以做"一键安装模型包"，把手动配置变成体验优势 |
| **openclaw** | 无 Live2D 能力（纯文本/执行层） | 不构成竞争 |
| **cc-haha** | 未知（推测为轻量桌宠） | 同上 |

**差异化机会**：做"人格 + 模型"绑定的主题包——下载一个角色不只是换皮，连说话风格、情绪偏好、默认动作集一起换。这是单纯的模型商城做不到的。

### 提案 2：技能创作者分成（Bounties）

#### 一句话定位

第三方开发者可以为 Lumina 开发技能插件（类似 VSCode Extension），用户按需付费或按调用量付费，开发者获得分成。解决"内置技能有限、长尾需求没人做"的问题。

#### 可行性评估：**中低**

**理由：**
- **技术上有基础但隔离不足**：当前技能系统（`skillLoader.ts` + `skillInstaller.ts`）已经支持从用户目录加载 SKILL.md，但工具实现（`.ts` 文件）需要在 `electron/tools/index.ts` 里手动注册——**第三方技能无法真正"即装即用"**，因为它们是编译进主进程的 TypeScript，不是运行时加载的插件。
- **沙箱隔离是硬骨头**：如果第三方技能能执行任意代码（shell 工具、文件操作），那就是在用户电脑上跑陌生人的代码。必须有严格的沙箱 + 权限声明 + 用户审批。
- **计费模型复杂**：按使用量分成需要埋点、对账、支付——这是一整套商业化基础设施，比配件商城更复杂（因为调用频次高、单价低）。

#### 技术要点

**核心实现思路：**

1. **技能运行时改造（最大工作量）**：
   - 当前架构：工具是编译时注册的 TypeScript 函数。
   - 目标架构：第三方技能打包成 `.lumina-skill` 包（本质是 zip），里面包含：
     ```
     my-skill.lumina-skill/
     ├── skill.json          # 元数据（名称、作者、权限声明、价格）
     ├── SKILL.md            # 给 LLM 看的说明书
     ├── index.js            # 运行时加载的实现（ESM）
     └── README.md
     ```
   - 主进程用 `vm.Module` 或 `isolated-vm` 在沙箱中加载 `index.js`，只暴露白名单 API（`lumina.http.get`、`lumina.storage.read` 等），不允许直接 require fs/child_process。
   - 权限声明机制：技能必须在 `skill.json` 里声明需要哪些权限（`network`、`filesystem.read`、`shell`），安装时用户审批。

2. **分成模式（二选一或组合）**：
   - **买断制**：技能定价 $1-$10，一次性购买永久使用。简单，类似 VSCode 付费扩展。
   - **订阅制**：技能按月订阅，或者按调用次数计费（调用 100 次以内免费，超出收费）。复杂，但适合高频工具类技能。
   - **建议**：MVP 先做买断制，简单可落地。

3. **技能市场前端**：
   - 复用现有的"技能商店"面板（UI 已有雏形），增加价格、购买按钮、开发者主页。

**关键技术选型：**
- 沙箱：`isolated-vm`（Node.js 原生隔离 V8 上下文，性能好）
- 包格式：zip + semver 版本号
- 支付：先做免费 + 捐赠入口，付费等商户号下来再做
- 审计：上传时自动跑 ESLint 安全规则（检测 `child_process`、`fs.write` 等危险调用），高危技能需人工审核

**需要配合的现有模块：**
- `electron/skills/skillLoader.ts` — 从"扫描 SKILL.md"升级为"加载并执行第三方技能包"
- `electron/tools/registry.ts` — 增加动态注册能力（当前是编译时静态注册）
- `electron/security/` — 新增技能沙箱和权限控制
- `src/panels/` — 技能商店面板增加付费相关 UI

#### 风险与挑战

| 风险类型 | 具体问题 | 严重度 |
|----------|----------|--------|
| **安全风险** | 第三方技能 = 桌面端 RCE 入口。即使有沙箱，也可能有逃逸漏洞（vm 沙箱历史上被绕过多次）。这是所有插件生态的阿喀琉斯之踵。 | 🔴 高 |
| **合规风险** | 涉及支付 + 数字商品销售，需要增值电信业务经营许可证（EDI 证），个人开发者基本拿不到，需要公司主体。 | 🔴 高 |
| **冷启动风险** | 没有用户就没有开发者，没有开发者就没有技能。这是双边市场经典的鸡生蛋问题。 | 🟡 中 |
| **质量风险** | 第三方技能质量参差不齐，可能导致 Lumina 崩溃。需要版本兼容检查 + 自动降级机制。 | 🟡 中 |

#### 优先级建议：**P3（远期）**

**理由：**
- 这是一个"生态级"功能，不是一个"功能级"功能。需要先有用户规模（至少几千活跃用户），否则做了也没人用。
- 前置依赖太多：沙箱隔离改造、支付系统、合规牌照，每一个都是大工程。
- v0.2 阶段先把"本地技能目录加载"做完善（让极客用户能手动装技能），作为生态的萌芽。
- 真正的市场和分成至少要等 v1.0 以后。

#### 与竞品对比

| 竞品 | 类似能力 | Lumina 差异化机会 |
|------|----------|-------------------|
| **N.E.K.O** | 有插件概念但未开放第三方开发 | 我们可以做"技能 = Agent 工具"的标准化，开发者写一个技能，Lumina/热茶/Yak 三个 Agent 都能用 |
| **AIRI** | 有 WebUI 插件系统，但主要是 UI 层面的扩展 | 我们的差异化是"Agent 可调用的工具技能"，不是"界面上多一个按钮" |
| **openclaw** | 本身就是执行网关，有 MCP 协议接入能力 | 我们可以做 MCP Server 的一键安装和付费市场——MCP 已经是事实标准，Lumina 可以成为 MCP 应用商店 |
| **cc-haha** | 未知 | — |

**差异化机会**：蹭 MCP 标准的东风。把 Lumina 技能市场做成"MCP Server 商店"——开发者写的技能天然就是 MCP Server，不仅 Lumina 能用，任何支持 MCP 的客户端都能用。这是生态级的定位。

### 提案 3：团队记忆共享（跨用户 Federation）

#### 一句话定位

不同用户的 Lumina 实例之间可以安全地共享记忆/知识/经验（比如"我把我的高效工作流记忆导出给你"），形成分布式的知识网络，而不是每个用户从零开始养一个 AI。

#### 可行性评估：**低**

**理由：**
- **隐私是红线中的红线**。记忆系统存的是用户的个人经历、偏好、甚至秘密。跨用户共享记忆 = 把用户最私密的数据暴露出去，合规风险极高。
- **技术复杂度极高**：需要端到端加密（E2EE）、P2P 发现协议、增量同步、冲突合并、信任网络（谁分享的记忆我要不要信）。这是 Signal + Secure Scuttlebutt 级别的工程量。
- **产品价值模糊**：用户真的想把自己的私人记忆共享给陌生人吗？大概率不想。更合理的场景是"用户主动导出某条记忆分享"，而不是"自动联邦"。

#### 技术要点

**核心实现思路（如果真要做的话）：**

1. **分层设计（从保守到激进）**：
   - **Level 1：手动导出/导入**（最简单）——用户在记忆剧场里选几条记忆，导出成 JSON 文件，发给朋友导入。零网络复杂度，零隐私风险。
   - **Level 2：公开记忆库**——用户可以选择把某些"公共知识"（比如"我总结的 ComfyUI 安装避坑指南"）发布到公共记忆池，其他用户可订阅。类似 Reddit 但结构化。
   - **Level 3：好友间联邦**——互加好友后，双方的 Lumina 可以同步标记为"可共享"的记忆。需要 E2EE + P2P。

2. **技术架构（Level 3 参考）**：
   - 身份：每个 Lumina 实例有一个密钥对（Ed25519），公钥即身份。
   - 传输：WebRTC DataChannel 做 P2P 加密通道（打洞失败时走 TURN 中继）。
   - 同步：基于 CRDT（Conflict-free Replicated Data Type）解决多端冲突，记忆条目是 append-only 的日志。
   - 信任模型：默认不信任任何远程记忆，导入时标记来源 + 置信度权重，LLM 引用时需要说明"这是来自好友 X 的经验"。

**需要配合的现有模块：**
- `electron/memory/memoryStore.ts` — 记忆存储层需要增加来源标签和信任分数
- `electron/memory/memoryStructured.ts` — 结构化记忆需要增加 `shared: true/false` 字段
- `src/panels/` — 记忆剧场面板需要增加"分享"按钮和来源标识

#### 风险与挑战

| 风险类型 | 具体问题 | 严重度 |
|----------|----------|--------|
| **隐私风险** | 最大风险。用户记忆中可能包含银行卡号、密码提示、家庭住址、健康状况。即使有 E2EE，如果用户误操作分享了敏感记忆，后果严重。 | 🔴 极高 |
| **合规风险** | 跨用户数据传输 = 数据出境/跨主体传输，需要符合《个人信息保护法》的个人信息共享要求。用户必须明确知情同意，且必须能随时撤回。 | 🔴 高 |
| **技术风险** | P2P 打洞成功率在国内网络环境下不高（NAT 类型复杂），需要中继服务器，成本和运维复杂度都上来了。 | 🟡 中 |
| **体验风险** | 记忆被"污染"——好友分享了错误信息，Lumina 当真了怎么办？需要记忆的可信度评分和用户纠错机制。 | 🟡 中 |

#### 优先级建议：**P3（远期）**

**理由：**
- 先做 Level 1（手动导出/导入记忆 JSON），这个零风险、一周能做完，先验证用户有没有这个需求。
- Level 2（公共记忆库）可以作为"社区知识库"来做，不需要做 P2P，只需要一个轻量后端。
- Level 3（自动联邦）至少是 v2.0 以后的事，等隐私计算和加密基础设施成熟了再说。

#### 与竞品对比

| 竞品 | 类似能力 | Lumina 差异化机会 |
|------|----------|-------------------|
| **N.E.K.O** | 有"五维记忆"概念，但完全是本地的，无跨用户共享 | 我们如果做了"可信任的记忆分享"，是降维打击——但前提是信任机制做得足够好 |
| **AIRI** | 无记忆系统（主要是实时反应） | 不构成竞争 |
| **openclaw** | 无记忆系统 | 不构成竞争 |
| **cc-haha** | 未知 | — |

**差异化机会**：短期来看，做一个"公共提示词/人格分享库"比"记忆共享"更现实——用户可以分享 SOUL.md、AGENTS.md 的配置，而不是分享自己的私人记忆。这既满足了社区分享需求，又不碰隐私红线。

### 提案 4：跨设备云同步（iCloud/OneDrive）

#### 一句话定位

用户在台式机上养的 Lumina，在笔记本上打开时，记忆、人格配置、技能安装状态全部同步过来。解决"换设备就像重新养了一个 AI"的割裂感。

#### 可行性评估：**高**

**理由：**
- **技术上非常成熟**：Electron 应用的云同步是一个老问题，有成熟方案（基于 WebDAV 的 Syncthing 风格、或者直接用各家的云盘 API）。
- **数据量可控**：Lumina 的核心数据是 SQLite 数据库 + Markdown 文件，总体积通常 < 50MB（记忆 + 配置 + 人格文件），同步成本很低。
- **不涉及 UGC 和支付**：纯用户自己的数据同步，合规风险低（用户数据归用户，只是帮他存到云上）。

#### 技术要点

**核心实现思路：**

1. **同步内容分层**（按频率和大小排序）：
   - **高频小文件**（每次启动同步）：人格配置（SOUL.md/PROFILE.md）、Agent 配置、情绪状态向量、设置项。
   - **中频中文件**（每小时/手动触发同步）：记忆数据库（SQLite）、对话历史摘要、自定义 Agent 配置。
   - **低频大文件**（用户手动触发）：Live2D 模型、安装的技能包、TTS 语音缓存。

2. **技术方案选型**：
   - **方案 A：WebDAV 通用方案（推荐 MVP）**
     - 让用户自己填 WebDAV 地址（坚果云、Nextcloud、自建 WebDAV 都行），Lumina 不做后端。
     - 优点：零服务器成本、用户自主选择存储位置、隐私可控（数据存在用户自己的云盘里）。
     - 缺点：用户需要手动配置 WebDAV，有一定门槛。
   - **方案 B：官方云（长期目标）**
     - 做一个简单的后端（Supabase/Supabase Edge Functions + Postgres），用户注册账号后自动同步。
     - 优点：体验好，一键登录自动同步。
     - 缺点：要做用户系统、要存用户数据（合规责任重）、服务器成本。

3. **冲突解决策略**：
   - SQLite 数据库不能直接合并。策略是：**以最后修改时间为准，整库覆盖**。用户两端同时改的概率不高（通常是一台主力机 + 一台备用机），冲突时弹窗让用户选"用这台的 / 用云端的 / 合并"。
   - Markdown 文件（SOUL.md 等）可以做行级 diff 合并，或者也用最后写入胜出策略。

**关键技术选型：**
- 同步协议：MVP 用 WebDAV（`webdav` npm 包）
- 增量同步：基于文件 hash + mtime，只传变化的文件
- 加密：同步前用用户密码做 AES-256 加密，云端看不到明文内容

**需要配合的现有模块：**
- `electron/main.ts` — 启动时加载云同步模块，退出前触发同步
- `electron/memory/memoryStore.ts` — SQLite 备份/恢复接口
- `src/panels/设置面板` — 增加云同步配置 UI
- `electron/skills/` — 技能安装状态需要同步（或者标记为"设备本地"不同步）

#### 风险与挑战

| 风险类型 | 具体问题 | 严重度 |
|----------|----------|--------|
| **数据安全风险** | 同步数据包含记忆（可能有敏感信息），如果传输或存储被攻破，用户隐私泄露。必须端到端加密。 | 🟡 中 |
| **同步冲突风险** | 两台设备同时编辑同一个文件，冲突处理不好会丢数据。需要"冲突检测 + 手动解决"的兜底机制。 | 🟡 中 |
| **用户体验风险** | 普通用户不知道 WebDAV 是什么。如果做官方云，又要注册账号，增加门槛。 | 🟢 低 |
| **技术风险** | SQLite 文件在同步过程中如果被占用（应用正在运行），上传的是不一致状态。需要先做 VACUUM 备份再上传。 | 🟢 低 |

#### 优先级建议：**P1（v0.2）**

**理由：**
- 这是一个"用户感知很强"的功能——用户有多台电脑的比例不低，每次换设备都要重新配置人格、重新积累记忆，体验断裂感很强。
- 技术成熟，MVP 用 WebDAV 方案 2-3 周就能做出来，投入产出比高。
- 不涉及 UGC、不涉及支付、不涉及第三方内容，合规风险低。
- 建议 v0.2 先做 WebDAV 通用方案，官方云等 v0.3 再说。

#### 与竞品对比

| 竞品 | 类似能力 | Lumina 差异化机会 |
|------|----------|-------------------|
| **N.E.K.O** | 有"跨设备记忆"概念（手机端 App 同步 PC 端） | 我们的差异化是"WebDAV 开放方案"——不绑定特定云服务，用户用自己的云盘，隐私和自主权都在用户手里 |
| **AIRI** | 本地优先，无云同步 | 我们做了就是差异化 |
| **openclaw** | 无（纯执行层） | — |
| **cc-haha** | 未知 | — |

**差异化机会**：主打"你的数据永远在你自己的云盘里"。对比 N.E.K.O 那种"数据存在我们服务器上"的模式，WebDAV 方案对隐私敏感用户有极强吸引力。

### 提案 5：插件 Marketplace 治理（npm + 木马扫描）

#### 一句话定位

为技能/插件市场建立安全治理体系：上传时自动扫描恶意代码、做数字签名、建立黑名单/白名单机制，防止用户安装带毒插件。这是做任何插件生态的前置安全基础设施。

#### 可行性评估：**中高**

**理由：**
- **静态分析技术成熟**：JavaScript/TypeScript 的静态安全扫描有成熟工具链（ESLint 自定义规则、esbuild 做 AST 分析、Socket.dev 做供应链检测）。
- **Electron 应用的插件安全有前车之鉴**：VSCode 的扩展沙箱、Figma 的插件审核，都是可参考的成熟模式。
- **不需要后端也能做 MVP**：先做客户端侧的"安装前扫描"——检测插件代码里有没有危险 API 调用，有就弹窗警告。

#### 技术要点

**核心实现思路：**

1. **多层防御体系**：

   ```
   上传时 → 自动扫描（静态分析）→ 人工抽检（高危包）→ 签名发布
   安装时 → 二次扫描（用户本地）→ 权限声明展示 → 用户确认
   运行时 → 沙箱隔离（限制 API 访问）→ 行为监控（异常上报）
   ```

2. **静态扫描规则（MVP 阶段就能做）**：
   - 检测 `child_process.exec` / `spawn` 调用 → 高危，弹窗警告
   - 检测 `fs.writeFile` 到敏感路径（`~/.ssh`、`~/.aws`、`%APPDATA%/Code/User/globalStorage`）→ 高危
   - 检测 `https.request` 到可疑域名（内置已知恶意域名列表）→ 中危
   - 检测 `require('electron').remote` → 高危（直接拿到主进程权限）
   - 依赖包检查：对比 package.json 里的依赖和 npm 上的最新版本，检测 typosquatting（比如 `lodashh` 仿冒 `lodash`）

3. **签名机制**：
   - 每个经过审核的技能包用 Lumina 的私钥做 RSA 签名
   - 用户安装时用内置的公钥验证签名，未签名的包标记为"未验证"并警告
   - 私钥离线保管（硬件安全模块或至少是加密的 KMS）

4. **运行时沙箱**：
   - 第三方技能在 `isolated-vm` 里执行，只能通过 `lumina.*` 白名单 API 访问能力
   - 网络请求需要域名白名单（技能声明它要访问哪些 API，用户审批）
   - 文件操作限制在技能自己的目录内，除非用户显式授权

**关键技术选型：**
- AST 分析：`@babel/parser` + 遍历（比 ESLint 更灵活）
- 沙箱：`isolated-vm`
- 签名：Node.js 内置 `crypto` 模块
- 威胁情报：可以接 Socket.dev 或 Snyk 的开源数据库（免费额度够用）

**需要配合的现有模块：**
- `electron/skills/skillInstaller.ts` — 安装流程中插入扫描步骤
- `electron/security/securityGuard.ts` — 扩展新的检测规则（当前有 8 类，需要加"插件包检测"这一类）
- `electron/tools/registry.ts` — 动态注册工具时加权限检查

#### 风险与挑战

| 风险类型 | 具体问题 | 严重度 |
|----------|----------|--------|
| **安全风险** | 沙箱逃逸是永远的猫鼠游戏。即使做了静态扫描，也可能有混淆代码绕过检测。必须接受"没有绝对安全"的现实，做到风险可控即可。 | 🔴 高 |
| **误报风险** | 扫描规则太严会把正常技能也拦下（比如一个 shell 技能本来就需要 child_process），需要分级：高危拦截、中危警告、低危放行。 | 🟡 中 |
| **运营成本** | 人工审核需要人。早期用户少可以自己审，用户多了就要建审核团队。 | 🟡 中 |
| **供应链风险** | 第三方技能依赖的 npm 包可能被投毒（event-stream 事件）。需要依赖树扫描 + 锁文件校验。 | 🟡 中 |

#### 优先级建议：**P1（v0.2）**

**理由：**
- 这是做任何插件生态的前置条件——没有安全治理就开放第三方插件，等于在用户电脑上装后门。
- MVP 阶段工作量不大（静态扫描规则 + 安装前警告弹窗），1-2 周就能出第一版。
- 即使现在还没有第三方插件市场，先把"安装本地未验证技能时弹出安全警告"这个机制做了，对现有用户也是保护。
- 签名机制可以等真的有官方市场了再加。

#### 与竞品对比

| 竞品 | 类似能力 | Lumina 差异化机会 |
|------|----------|-------------------|
| **VSCode** | 成熟的扩展审核 + 沙箱 | 我们不需要做到 VSCode 级别，先做"够用的安全网"就行 |
| **N.E.K.O** | 无第三方插件生态 | 我们做了就是领先半个身位 |
| **AIRI** | 有插件但审核宽松 | 我们的"安全可信"可以作为卖点 |
| **openclaw** | MCP 生态本身就有安全争议 | Lumina 可以主打"安全可控的 MCP 客户端" |

**差异化机会**：把"安全"做成卖点——"Lumina 的技能市场是所有桌宠里审核最严的"。在大家都在比谁功能多的时候，打安全牌反而能吸引注重隐私的用户。

### 提案 6：AI 主动推送（亲密度+疲劳+精力）

#### 一句话定位

Lumina 不再只是"你问她才答"，而是基于用户状态模型（亲密度、用户疲劳度、Lumina 自身精力值）主动发起对话、提醒、关怀。比如"你已经写了三小时代码了，休息一下吧"或者"今天还没跟我聊天呢，忙吗？"。

#### 可行性评估：**高**

**理由：**
- **现有基础很好**：架构文档里已经有 `proactiveEngine.ts`（主动行为引擎，约 1440 行）、`agentSocialEngine.ts`（社交引擎）、五维情绪追踪（开心/疲惫/专注/焦虑/好奇）、桌宠自主心跳（每 8 秒一次的 autonomy tick）。基础设施已经在了，缺的是"状态模型驱动的更智能的主动决策"。
- **技术不复杂**：本质是一个状态机 + LLM 决策。把用户状态（idle 时长、当前窗口、一天中的时间）和 Lumina 状态（亲密度、情绪向量、精力值）喂给 LLM，让它决定"现在要不要主动说话、说什么、用什么强度"。
- **用户感知极强**：这是"她真的活着吗"的关键体验。做不好会很烦人（弹窗轰炸），做好了会很暖心。

#### 技术要点

**核心实现思路：**

1. **状态模型（三维核心）**：

   | 状态 | 来源 | 取值范围 |
   |------|------|----------|
   | **用户疲劳度** | idle 时长 + 当前活跃窗口类型（写代码 vs 看视频 vs 打游戏）+ 时间（深夜加权） | 0-100 |
   | **亲密度** | 累计对话轮数 + 主动互动频次 + 用户给的正反馈（点赞、表情） | 0-100 |
   | **Lumina 精力值** | 距离上次主动推送的时间 + 上次对话情绪 + 一天中的"作息"（深夜她也会困） | 0-100 |

2. **主动推送决策逻辑**：
   ```
   每 15 分钟 tick 一次：
     1. 收集状态：用户在干嘛？多久没说话了？现在几点？
     2. 计算"推送欲望值" = 亲密度权重 × 话题新鲜度 × 精力值 × 场景匹配度
     3. 如果欲望值 > 阈值，且距离上次主动推送 > 冷却时间：
        → 让 LLM 生成一条符合当前场景的消息
        → 通过桌宠气泡 / 系统通知推送给用户
     4. 如果用户 30 分钟内没回应，自动降低下次推送的概率（避免烦人）
   ```

3. **关键体验细节**：
   - **绝对不能弹窗打断**：主动消息只走桌宠气泡和侧边栏，不弹系统通知（除非是用户明确开启的提醒类消息，比如"该喝水了"）。
   - **频率上限**：一天主动推送不超过 5 条，且间隔至少 30 分钟。用户可在设置里调频率。
   - **沉默也是一种选择**：不是每次 tick 都要说话。LLM 可以输出 `should_speak: false`，这本身就是"生命体感"——她在陪你，但不打扰你。
   - **亲密度影响说话方式**：亲密度低时只说"嗯，在忙吗？"；亲密度高了会吐槽"你又在摸鱼！"

**关键技术选型：**
- 复用现有的 `proactiveEngine.ts` 做状态收集和触发
- 复用 `intentDispatcher` 的 LLM JSON 输出协议（`{action, mood, speech, should_speak}`）
- 情绪向量已经在做（第 2 层设计），直接接上即可

**需要配合的现有模块：**
- `electron/proactive/orchestrator.ts` — 主动引擎增加状态模型输入
- `electron/pet/intentDispatcher.ts` — 输出 schema 增加 `should_speak` 和 `intensity` 字段
- `src/stores/` — 增加亲密度、精力值的状态管理
- `src/panels/设置面板` — 增加主动推送频率、时间段、类型的开关

#### 风险与挑战

| 风险类型 | 具体问题 | 严重度 |
|----------|----------|--------|
| **骚扰风险** | 主动推送做不好就是广告弹窗。用户会觉得"这 AI 怎么比我妈还唠叨"，直接卸载。 | 🔴 高 |
| **用户体验风险** | 推送时机不对（比如用户正在打 boss 战，桌宠突然蹦出来说"休息一下"）。需要感知用户当前是否在全屏游戏/演示。 | 🟡 中 |
| **技术风险** | LLM 生成的主动消息可能很尬（"主人你今天还没和我说话呢～"）。需要好的 prompt 工程 + 大量调优。 | 🟡 中 |
| **隐私风险** | 主动推送需要知道用户在干什么（当前窗口、idle 时间），如果处理不好会让用户觉得被监控。必须本地处理、不上传、可关闭。 | 🟡 中 |

#### 优先级建议：**P0（立即做）**

**理由：**
- 这是 Lumina 核心差异化的"最后一公里"——架构文档里写的"LLM 驱动身体"已经做了，但"主动陪伴"还停留在基础版。
- 技术上大部分基础设施已经存在，只需要把状态模型和决策逻辑补上，1-2 周就能出效果。
- 用户对"AI 主动找你聊天"的感知极强——做一个好的主动推送 demo，比写十页 README 都有说服力。
- 这是 v0.2 版本最好的"主打故事"。

#### 与竞品对比

| 竞品 | 类似能力 | Lumina 差异化机会 |
|------|----------|-------------------|
| **N.E.K.O** | 有屏幕搭话能力，基于场景规则触发 | 我们的差异化是"状态驱动 + 情绪惯性"——她不是看到你写代码就说"加油"，而是记得你昨天熬了夜，今天看到你还在写会担心 |
| **AIRI** | 主动能力弱，主要是被动响应 | 我们做了就是代差 |
| **openclaw** | 纯执行层，无主动人格 | 不构成竞争 |
| **cc-haha** | 未知 | — |

**差异化机会**：把"主动"做成有记忆、有情绪、有分寸的。不是定时弹窗，而是"她真的在关心你"。这是所有桌宠都想做但没做好的点。

### 提案 7：无障碍语音交互

#### 一句话定位

全语音操控 Lumina（"Lumina，帮我查一下今天股价"）+ 全语音反馈（TTS 播报回复）+ 屏幕阅读器兼容 + 低视力模式。让视力障碍用户和双手忙不过来的用户也能流畅使用。

#### 可行性评估：**中**

**理由：**
- **基础能力已有**：架构里有 `stt-server/`（STT 服务）、有 edge-tts / Kokoro 的 TTS 集成、桌宠已经有语音播报能力。
- **但"全语音操控"是另一回事**：当前语音是"你说一句它答一句"，要做到"像 Siri 一样全程语音操控"，需要连续对话、语音指令路由、多轮上下文、语音确认——这是一整套语音交互设计。
- **无障碍适配是细致活**：ARIA 标签、键盘导航、屏幕阅读器兼容、高对比度模式——技术不难，但工作量大，且容易被忽略。

#### 技术要点

**核心实现思路：**

1. **语音交互闭环**：
   ```
   唤醒词（"Lumina"）→ STT 识别 → 意图解析 → 执行 → TTS 播报 → 等下一句
   ```
   - 唤醒词：Porcupine（Picovoice）做离线唤醒词检测，精度高、离线可用。
   - STT：当前已有 `stt-server/`（推测是 Whisper.cpp 或类似本地 STT），直接复用。
   - 意图路由：把语音指令走现有的 Agent Runner，让 LLM 理解意图并调用工具。
   - TTS：edge-tts 已有，直接播报回复文本。

2. **无障碍 UI 适配**：
   - 所有交互元素加 ARIA label（屏幕阅读器能读出来）
   - 支持完整键盘导航（Tab 切换、Enter 确认、Esc 取消）
   - 高对比度模式：UnoCSS 加一套 `[data-theme="high-contrast"]` 变量
   - 字号缩放：整体 UI 支持 100%/125%/150% 三档

**关键技术选型：**
- 唤醒词：Picovoice Porcupine（免费额度够个人用）
- STT：复用现有 stt-server
- TTS：复用 edge-tts
- 无障碍：遵循 WCAG 2.1 AA 标准

**需要配合的现有模块：**
- `stt-server/` — 连续语音识别模式（VAD 端点检测）
- `src/panels/` — 所有面板加 ARIA 标签（工作量大但机械）
- `electron/main.ts` — 全局快捷键触发语音模式
- 桌宠窗口 — 语音交互时桌宠要有"正在听/正在想/正在说"的视觉反馈

#### 风险与挑战

| 风险类型 | 具体问题 | 严重度 |
|----------|----------|--------|
| **识别准确率风险** | 中文方言、嘈杂环境下 STT 准确率下降，用户体验差。 | 🟡 中 |
| **延迟风险** | 语音交互对延迟敏感（>1.5 秒就感觉卡）。本地 STT + 本地 LLM 才行，云端 API 延迟会很难受。 | 🟡 中 |
| **无障碍合规风险** | 如果面向海外用户，美国 ADA 法案要求软件无障碍。国内暂无强制要求，但作为加分项值得做。 | 🟢 低 |
| **开发工作量风险** | 全 UI 加 ARIA 标签是体力活，容易漏。需要系统地过一遍 23+ 个面板。 | 🟡 中 |

#### 优先级建议：**P2（v0.3）**

**理由：**
- 语音交互的核心（STT + TTS）已经有了基础，v0.2 可以先做一个"语音输入按钮"（按住说话）作为 MVP。
- 全语音操控和无障碍 UI 是打磨品质的事，不是核心差异化功能。先把核心体验做好，再补无障碍。
- 海外用户群体对无障碍敏感度更高，如果未来做海外市场，这个优先级会上升。

#### 与竞品对比

| 竞品 | 类似能力 | Lumina 差异化机会 |
|------|----------|-------------------|
| **N.E.K.O** | 有语音交互（VOICEVOX TTS），但主要是单向播报，语音操控弱 | 我们可以做双向语音对话——不只是她跟你说话，你也能语音指挥她干活 |
| **AIRI** | 有语音对话能力，WebGPU + 实时语音 | 我们的差异化是语音 + 桌面操控联动（"Lumina，帮我把这个文件移到桌面"） |
| **openclaw** | 纯文本 | 不构成竞争 |
| **cc-haha** | 未知 | — |

**差异化机会**：做"能干活的语音助手"。Siri 不能帮你写代码、不能帮你操作电脑，Lumina 可以。语音只是入口，背后的 Agent 能力才是壁垒。

### 提案 8：主题皮肤生态

#### 一句话定位

用户可以自定义 Lumina 的 UI 主题色、桌宠气泡样式、聊天背景，甚至打包分享完整主题包。解决"每个人的 Lumina 应该有每个人的味道"的个性化需求。

#### 可行性评估：**高**

**理由：**
- **技术上最简单**：当前用的是 UnoCSS，主题切换本质上就是换一组 CSS 变量。这是 8 个提案里技术门槛最低的。
- **用户感知直接**：换个主题立刻看到效果，即时满足感强。
- **不涉及后端**：MVP 完全可以本地做（用户自己调颜色、保存主题、导出 JSON 分享），不需要云服务。

#### 技术要点

**核心实现思路：**

1. **主题系统架构**：
   ```
   主题包 (theme.lumina-theme) = JSON 文件
   {
     "name": "暗夜霓虹",
     "author": "xxx",
     "colors": {
       "primary": "#ff6b9d",
       "background": "#0a0a0f",
       "surface": "#1a1a2e",
       "text": "#e0e0e0"
     },
     "pet": {
       "bubbleStyle": "rounded",
       "bubbleColor": "#ff6b9d",
       "font": "霞鹜文楷"
     },
     "chat": {
       "background": "url(...) 或 渐变色",
       "bubbleRadius": 12
     }
   }
   ```

2. **实现方式**：
   - UnoCSS 主题配置已经是 CSS 变量驱动的，只需要在 `:root` 上切换变量值即可。
   - 主题编辑器：做一个可视化面板，色盘选色 + 实时预览 + 保存为主题包。
   - 分享：导出 `.lumina-theme` 文件（本质是 JSON），用户可以发到社区，别人双击导入。

3. **进阶（v0.3）**：
   - 主题市场：上传主题到云端，一键安装。
   - Live2D 皮肤主题：和提案 1 联动——一个主题包 = UI 配色 + 桌宠模型 + 气泡样式。

**关键技术选型：**
- 样式：UnoCSS CSS 变量（已有基础）
- 色板：`react-colorful`（轻量色盘组件）
- 预览：主题编辑器里实时渲染一个迷你聊天窗口预览

**需要配合的现有模块：**
- `src/stores/appStore.ts` — 当前主题状态管理
- `src/panels/设置面板` — 主题编辑器 UI
- `uno.config.ts` — 扩展主题变量
- 桌宠窗口 — 气泡样式也需要跟随主题

#### 风险与挑战

| 风险类型 | 具体问题 | 严重度 |
|----------|----------|--------|
| **设计一致性风险** | 用户自定义的配色可能丑到爆炸（亮粉配荧光绿），但那是用户的自由。提供预设主题兜底。 | 🟢 低 |
| **工作量风险** | 给所有 23+ 个面板都做主题适配，需要确保每个面板都用了 CSS 变量而不是硬编码颜色。如果现有代码里硬编码颜色很多，改造工作量会超预期。 | 🟡 中 |
| **兼容性风险** | 深色/浅色模式切换、高对比度模式和主题模式的关系需要理清，否则会乱。 | 🟢 低 |

#### 优先级建议：**P1（v0.2）**

**理由：**
- 技术最简单、用户感知最强、投入产出比最高。2-3 周就能做出来。
- 个性化是桌宠类产品的核心情感需求——"我的 Lumina 和你的不一样"。
- 可以和提案 1（Live2D 配件商城）形成协同：v0.2 先做主题分享，v0.3 扩展到模型和动作包。

#### 与竞品对比

| 竞品 | 类似能力 | Lumina 差异化机会 |
|------|----------|-------------------|
| **N.E.K.O** | 有主题色切换，但无主题分享生态 | 我们做"主题包一键分享 + 安装"就是差异化 |
| **AIRI** | 主要是 Live2D 模型换皮，UI 主题弱 | 我们 UI + 桌宠一起换，更完整 |
| **openclaw** | 无 UI | — |
| **cc-haha** | 未知 | — |

**差异化机会**：做"人格 + 外观"一体化主题包。不只是换颜色，连桌宠的说话气泡样式、聊天背景、情绪条颜色都一起换。一个主题 = 一种氛围。
