0. TL;DR（先给结论）

  • 一句话定位：Lumina 是"有身体的团队 Agent"——一个把「多 Agent 协作 + 真实情绪数值 + 桌宠形象 + 记忆 + 桌面操控」捏在同一个 Electron 应用里的项目。这个交集在本次对标的 4 个项目里确实没有第二个同时占满。
  • 工程质量是真的，但"全绿"有水分（我亲自跑出来的）：tsc --noEmit --strict 0 error 稳定复现；vitest 我连跑三次，结果分别是 3517 全通过 / 3516 通过·1 失败 / 3488 通过·9 失败（并发负载下）——套件是"flaky"（时序/负载敏感的间歇性失败），不是 README 宣称的确定性全绿。对一个 0-star、单作者的项目，底座仍属高水位，但"3514 全绿"这句需要改成"快机器上通常绿"。
  • Agent 团队是真的，不是 PPT：独立 Runner、并发对抗评审、角色硬权限闸门、ReAct 循环保护、动态雇工 + git worktree 隔离——全部是可读、可测的真实代码。
  • 但"问到什么就能解决什么"做不到 100%：具体任务（写码 / 修 bug / 审查 / 文件 / 搜索 / 定时 / 记忆）稳定能做好；模糊开放式任务、需要品味的任务、跨平台桌面操控、第三方技能生态会打折或做不到。路由是"LLM 建议"而非"确定性调度器"，同一问题两次可能派活不同。
  • 最大结构性风险不是功能，是"单作者 + 0 社区 + 仅 Windows 实机"：直接对手 N.E.K.O 已上 Steam（appid 4099310），上游 openclaw 有 39.1 万 star / 周均 2000+ 提交。0 → 第一个 1000 star 靠的是内容与分发，不是继续堆功能。
  • 发布就绪度判定：功能层面接近可发（P0 级阻断项在最新 HEAD 已基本清空）；产品层面"未验证"。本报告给出 9 条可落地改进项。

1.5 一处需要更正的表述：Chromium 沙箱其实是关闭的

我读码发现一处注释与代码自相矛盾：

  • electron/main.ts:239 明确写着 sandbox: false（渲染进程的 Chromium 沙箱关闭）；
  • 但 electron/main.ts:541 的注释却写「安全已通过 webPreferences 保障（contextIsolation + nodeIntegration:false + sandbox）」；
  • README 的「智能沙箱」章节讲的是应用层的 sandboxRules.ts / securityGuard（命令规则、审批流），不是 Chromium 沙箱。

这不是漏洞，但需要如实表述：Lumina 的安全来自「应用层规则库 + 权限闸门 + 审批流」，不是「浏览器沙箱」。sandbox:false 在需要 preload 直接用 Node API 的 Electron 应用里很常见，但它与那句"已通过 sandbox 保障"的注释不符，建议二者对齐（改注释或改配置），避免安全审计时被指为"安全声明与实现不符"。

2. Agent 与多 Agent 协作机制（核心章节）

2.1 三个 Agent 与"铁则"

Agent角色对用户可见工具边界职责
-------------------------:----:----------------------------------------------------------
Lumina 🐱boss✅ 唯一入口全量放行对话 · 情绪 · 派活 · 整理结果
Yak 💻worker❌ 隐身可写/可执行/可提交（YAK_ALLOW），禁二次委托写码 · 调 bug · 重构 · 跑测试
热茶 (Recha) 🍵worker❌ 隐身只读（RECHA_ALLOW），显式 deny 写/执行/提交审查 · 挑错 · 风险评估

三条铁则（AGENTS.md）：① 用户只跟 Lumina 说话；② Worker 不主动跟用户说话、不直接返回结果；③ Worker 之间不直接对话，通信经 Lumina 转发。这是一&#x4E2A;"单入口 + 隐身团队"&#x7684;产品判断，与 openclaw 的"多 session 各自可见"、cc-haha 的"泳道可视化"是不同路线。

2.2 单 Agent 运行机制

  • 独立 Runner：main.ts 启动时为 yak/recha 各建常驻 AgentRunner；每个 worker 真起独立实例（不是同一 prompt 换皮）。
  • 工具调用协议：core/reactEngine.ts 同时支持 XML 解析路径 + JSON function-calling 路径，两条路径都调用 checkRoleGate()。
  • 人格来源：agentTeamPersonas.ts（主 system prompt）+ electron/agents/<id>/{AGENTS,SOUL,PROFILE,MEMORY}.md 每人 4 件套身份文件。
  • 循环保护：agentRunner.ts maxRounds=30（注释写明从 200 降下来防空转）；同一工具 ≥5 次封禁 2 轮；>30 强制收敛。
  • 弱模型降级：weakModelMode.ts 对 ≤7B 模型自动进入"轻量模式"——只留记忆/搜索/只读文件等安全工具，砍掉 delegate_* 与写/执行类，并提示模型直接简洁回答。

2.4 自定义 Agent 扩展

electron/agents/customAgentManager.ts + docs/custom-agent-guide.md：用户可创建自定义 Agent（一个文件夹 = agent.json + SOUL.md + PROFILE.md + MEMORY.md），指定 teamRole（leader 可对用户可见并设为默认主对话对象 / member 进团队被委托 / solo 独立存在）、独立模型、工具白名单。这是把"三 Agent 硬编码团队"升级为"可扩展团队"的正确方向，但同样受制于"委托由模型裁量"这一点。

3.2 🔴 N.E.K.O —— 唯一 ~85% 重叠的镜像对手

它是什么：Python 3.11 + FastAPI 的三服务器架构，一只会主动找你玩的 AI 猫娘桌宠，由"具身情感引擎"驱动。官方文档明确的三个核心进程：

服务端口职责
---------------------------:------------------------------------------
Main Server48911Web UI / REST / WebSocket / 逐角色会话 / 外部 TTS
Memory Server48912对话接收 / 近期上下文 / 事实·反思·persona / 启动上下文渲染与召回
Agent / Tool Server48915能力状态 / 任务评估 / 通道分派 / 取消与任务结果

通信：HTTP + WebSocket 承载服务与浏览器流量；ZeroMQ（PUB :48961 / PUSH :48963 / PULL :48962）承载 Agent 事件桥；Agent 进程内还嵌一个 user-plugin FastAPI（:48916）。

  • 它最强：记忆系统的工程深度（memory/ 35+ 模块：evidence / hybrid_recall / embedding_worker / persona 融合自修正 / speaker_trust / anti_repeat / memory_browser 校对 UI）；分发已跑通（Steam appid 4099310 + 创意工坊）；五形态 Avatar；Python 后端与桌面壳解耦。
  • 它比 Lumina 弱：① 单角色（猫娘 YUI 一个人做所有事，没有多 Agent 团队结构）；② 没有 Agent 间关系记忆（亲密度/信任随真实委托演化）；③ 没有分级沙箱。
  • 结论：记忆赛道不要硬拼（它是行业最深的那一个，Lumina README 自己也承认"证据链不是我们的发明"）。Lumina 的正确打法是守"多 Agent + 情绪数值 + 桌宠绑真实状态"。

3.3 🟠 AIRI —— 形象工程的巨人，记忆上的弱者

它是什么：TypeScript 单体仓库（monorepo，40+ packages），受 Neuro-sama 启发的开源 AI VTuber / 数字生命容器。三个 App 共享同一 domain 层：stage-web（浏览器/PWA）、stage-tamagotchi（Electron 桌面）、stage-pocket（移动，Capacitor）。

  • 它最强：同一份 domain 层驱动三端；渲染后端最全（Live2D / VRM / MMD / Spine / Tachie 立绘）；多模型供应商经 xsAI 抽象层；VAD + STT + TTS 语音管线；Minecraft（mineflayer）自主游玩；6 语言 i18n + Crowdin；winget / brew / nix 全渠道分发；server-runtime/server-sdk 用 crossws 做实时通信。
  • 它最弱（恰是 Lumina 强项）：官方 Roadmap 上 Memory Alaya 仍标 [ ] 未勾选（一个主打"数字生命"的项目，"记得你"那一格还没做完）。记忆底层有 DuckDB WASM（浏览器内）+ pgvector 两套后端，但"Alaya"编排层仍是 WIP。
  • Agent 机制：core-agent 单编排器 + typed tools，不是多 Agent 蜂群；靠插件做能力编排。
  • 结论：Lumina 的"记忆就绪"相对 AIRI 是真实领先，但前提是不踩自己"记忆曾为死代码"的老坑（现已修，需保持）。

3.4 🔵 openclaw —— 别当对手，当上游标准制定者

它是什么：由 Peter Steinberger 发起、现由 OpenClaw Foundation（501(c)(3)） 治理的常驻 Gateway 守护进程 + 多客户端体系（不是 Electron）。TypeScript + Node，WebSocket 协议（ws://127.0.0.1:18789）。四层结构：Channel（20+ 渠道）→ Gateway 控制面 → LLM Brain（25+ 模型）→ Skills 工具箱。

  • Agent 机制：是多 Agent 路由（不是团队协作）——每个 agent = 独立 workspace + agentDir + SQLite session db；按 (channel, accountId, peer) 做确定性绑定路由；子 agent 经 sessions_spawn；agent-to-agent 工具默认关闭。
  • 记忆：刻意做成纯 Markdown（MEMORY.md / memory/YYYY-MM-DD.md / DREAMS.md），检索用 vector + BM25 + 时间衰减 + MMR 混合，默认 SQLite 后端 + OpenAI embedding；有 Dreaming 后台整理。
  • 它最强：生态规模大三个数量级（39.1 万 star、周均 2000+ 提交）、32 个渠道、ClawHub 技能市场、节点配对安全体系、TypeBox→JSON Schema→Swift 同源代码生成。
  • 它最弱：零人格 / 零形象 / 零情绪。
  • 结论：不是竞争是上游。Lumina 可选两条路：做它的 A2A adapter 借渠道；或在 IM 层做它做不到的差异化（带表情、带语音、带桌宠状态的 IM 交互）。

3.5 🔵 cc-haha —— 工程参考书，但有法务暗礁

它是什么：桌面端 Claude Code 工作台（"Claude Code 在中国开发者场景下的全栈再发行版"）。Electron + React + Vite + Zustand；本地运行时 Bun；四类进程（Electron 主 / 渲染 / claude-sidecar（Bun.serve HTTP+WS，每会话 spawn 一个 CLI 子进程）/ IM 适配器）。

  • 它最强：可视化多 Agent 工程台的完整度——Agent Teams 依赖泳道画布 · 动态 Workflow 现场编排（模型写编排脚本）· 模型 trace 面板 · Worktree 隔离启动 · 逐文件 diff 审查 · 内置带登录态浏览器预览 · 5 级权限 · IM 8 渠道（微信/飞书/钉钉/Telegram/WhatsApp/企微/QQ/Slack）+ H5 远程。内置 6 个 agent（general-purpose / Explore / Plan / verification / claude-code-guide / statusline-setup），Agent 工具支持 subagent_type/model/background/worktree 与并行，>120s 自动转后台；Agent Teams 用 TeamCreate→成员→SendMessage（定向/广播）→shutdown_request/response→TeamDelete。
  • 它最弱 / 风险：① 本质是 Claude Code 的 GUI 外壳，记忆 100% 继承 Claude Code（自己无独立记忆层）；② 基于泄露/逆向的 Claude Code 源码构建 → 法律与合规灰区（这是 Lumina 应当避开、也应提醒用户注意的一条）；③ 作者自己写明桌宠"只是状态提示和跳转入口，不能替你批准权限"——Lumina 恰好越过了这条线（详见 §4.3）。
  • 结论：可视化编排（泳道 / Workflow / trace）是 Lumina 明确该抄的作业；其商业绑定（靠 API 中转站赞助）是 Lumina 商业化应避开的路径。

4.1 优势（按可持续性排序）

5. 维度二：竞争力、创新性与创意亮点

5.1 竞争力（相对定位）

Lumina 的竞争力不在"功能多"（功能数量上它被 openclaw/cc-haha 碾压），而&#x5728;"功能组合的唯一性"：它是唯一把"多 Agent 团队 + 情绪数值 + 桌宠形象 + 记忆 + 桌面操控 + 主动性"全部塞进一个常驻桌面应用的项目。&#x5BF9;"想要一个会陪我、又会帮我干活的桌面伙伴"&#x7684;人群，它是当前几乎唯一的开源选择。而&#x5BF9;"想要最强 coding agent"&#x7684;人群，它竞争力弱于 cc-haha/openclaw——这不是同一批用户。

5.2 创新性（真正独特的）

  • 桌宠状态桥（pet/agentStateBridge.ts）：把"任务生命周期"翻译成"身体动作"，纯函数、零 token。这是一个别人没做的架构选择。
  • 情绪门控的"只收紧"不变量：把"情绪能不能解锁权限"这个安全问题，用"结构上只有减法"直接消灭——不是靠策略，是靠类型/接口设计。
  • LLM 驱动身体（{action, mood, speech} 单次推理同时决定动作+表情+台词）：与"定时器播动画 + 另一模块生成台词"的本质区别，且有 [Brain] 日志可验证。
  • 证据桥（evidenceBridge.ts）：把写入期权威性（source 决定）与读取期五维证据评分接通，且不改写任一套，不变式是"不引入第二个谁说了算"。

5.3 创意亮点（差异化彩蛋）

  • 团队社交生活：群聊 / 早安仪式 / Moments 朋友圈 / 关系演化（亲密度影响热茶审查语气）。
  • 主动性引擎：8 类定时器，数据源是真实网络请求（B 站 + 微博 + arXiv）；门控齐全（触发门 / 指数退避 / 未完成话题 / 内心独白）。
  • 游戏陪伴：视觉路线（截图→VLM→键鼠）开箱即用，Minecraft/Factorio 已适配；Mineflayer 程序化控制为可选扩展。
  • 桌面沙箱玻璃房：实时显示每条命令命中的级别 / 威胁类别 / 处置。
  • 可解释情绪（emotionAudit.ts）："她为什么不帮我"可被解释，用户可放行这一轮（不是永久解锁）。
  • 梦境日记 / 真人秀 / 成就系统：featureManifest.ts 诚实标注为 experimental（"模板兜底"），不冒充 AI 输出。

6. 维度三：普通用户 vs 专业用户模拟体验

6.1 普通用户（画像：想"有个会陪我、偶尔帮我"的桌宠）

上手：Windows 下载安装包，3 分钟上手（发布后）。默认三个 Agent 已预填云端 Provider（Lumina→硅基流动 / Yak→DeepSeek / Recha→智谱），填 API Key 即可，新手无需装本地推理——这是比"必须装 LM Studio"友好得多的默认路径。

日常体验：桌宠主动关心（"盯着屏幕好久了，休息一下？"）、记得你上周说过的事、帮你定闹钟/搜东西/整理文件；情绪有连续余韵（被怼了会先顿一下再小声回）；后台 Yak/热茶在"朋友圈"里互动（可旁观）。

能爽到的：陪伴感、记忆延续、简单自动化、偶尔帮你点两下鼠标。

会踩的雷：

  1. macOS / Linux 用不了（仅 Windows 实机验证）。
  2. "完全本地"要自己装 LM Studio/Ollama（应用不内置推理）。
  3. 第三方技能市场是空的（通道通了，生态没内容）。
  4. IM 只有 Telegram 验证过，想用微信/钉钉得自配凭据且没真机验证。
  5. 首 token 慢时要用 lumina health 自查（多半是上下文窗口填太大）。
  6. 空载内存 ~775MB（5 进程），4GB 机器会紧张。

普通用户结论："陪伴 + 轻助手"场景体验可以打到 7.5/10，但平台限制和生态空白是硬门槛。

6.2 专业用户（画像：开发者/工程师，想"让它真帮我写码"）

能稳定做好的：

  • 写/改/调试/重构代码（派 Yak，自动跑 tsc + 测试，不通过自己修）
  • 代码审查与风险评估（热茶多视角并发对抗评审 + 完整性批评员）
  • 跨会话记忆（BM25 + TF-IDF 双路 RRF 融合 + 证据链重排）
  • 桌面点击/输入/快捷键/截图 OCR、文件与搜索、git、网页抓取、定时任务
  • MCP 扩展、CLI（lumina chat/tool/agent/memory）、REST API（10+ 端点）

会打折的：

  1. 模糊任务（"优化一下这个项目"）——vagueTaskGuard 会先问再动，但可能仍过度编排或降级。
  2. 需要品味的任务（UI 设计、文案润色）——弱。
  3. 多轮复杂重构——phase_gate_delegate 不在常驻工具组且人格提示词没教，模型几乎不会主动走五阶段。
  4. 跨文件依赖图展开——刚接线，未经真实任务验证。
  5. 沙箱缺命令归一化（decodeURI/base64/反斜杠），跑不可信脚本要小心（见 §8.4）。

最大爽点：后台 Yak+热茶流水线"写码 → 自动审查 → 自动修复"，而你只跟 Lumina 聊，看不到后台撕逼。

最大顾虑：单作者 + 0 社区——遇到 bug 没人帮你，只能等作者（巴士系数 = 1）。

专业用户结论："具体 coding 任务"体验可打到 8/10，&#x4F46;"模糊/品味/跨平台"任务会掉到 5~6 分。

6.3 两类用户共同的关键决策点

  • 要不要接受"只看到 Lumina"？ 想要透明编排的专业用户会觉得"藏起来"不透明；想要简单陪伴的用户会觉得这正是优点。
  • 要不要接受"路由不可预测"？ 同一问题两次可能派活不同——对追求可复现的专业用户是减分项。
  • 要不要接受"仅 Windows"？ 对 macOS/Linux 用户是一票否决。

  4. 需要品味/模糊的任务：模型本身的能力上限 + 缺少真实用户数据校准。

  • ⚠️ 情绪无连续昼夜节律（仅二值开关）
